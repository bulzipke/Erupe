# 특별 수렵단방: 요리와 티켓 교환 검증

2026-09-23. 운영 DB·클라이언트·보수량은 수정하지 않았습니다.
특별방 기능이 이미 클라이언트에 들어 있는 부분과 서버 작업이 필요한 부분을
구분한 기록입니다. 특별방 입장 자격과 선율 76종 교환은 기존 구현을 사용합니다.

## 요리: 추가 확률 패킷이나 강제 대성공은 필요하지 않습니다

[최종 공식 매뉴얼](https://web.archive.org/web/20191218054658id_/http://cog-members.mhf-z.jp/sp/manual/page399.html)은
특별방을 수렵단 랭크와 무관한 시설 이용, 요리 대성공이 쉬워지는 혜택으로
설명합니다. **대성공 보장**이라고 설명하지 않습니다.

Ghidra 로컬 8089에서 `mhfo-hd.dll.clean.mapped.bin`을 읽기 전용으로 확인했습니다.

| 함수 | 확인 내용 |
| --- | --- |
| `11555500` | 실제 가영 기간 및 서버가 내려준 특별방 자격 플래그로 지도 `445 (0x1BD)`를 선택합니다. |
| `107f7070` → `107f5310` | 요리 미니게임 판정 영역을 설정합니다. 지도 445에서는 `param+0x4A` 영역 폭을 두 배로 만듭니다. 요리 보조 옵션 3의 두 배 처리와도 별개의 기존 분기입니다. |
| `107f69b0` | 선택한 요리 재료를 클라이언트 아이템 보관함에서 소비합니다. |
| `107f4910` | 클라이언트 데이터 테이블 `DAT_1e77dcc4+0x868`에서 요리 ID·결과별 스킬을 선택하고 발동 시각을 저장합니다. |
| `114f76f0` | `REGIST_GUILD_COOKING (0x111)`에 덮어쓸 보관 ID, 완성된 요리 ID, 완성 결과를 보냅니다. 성공 확률 필드는 없습니다. |
| `1152be60` → `1152bd00` | `LOAD_GUILD_COOKING (0x110)` 응답을 보관함 최대 6건으로 읽습니다. 항목은 ID·요리 ID·결과·생성 시각의 4개 uint32입니다. |
| `107f9f00` / `107f9b00` | 보관 시각에 3,600초를 적용해 만료된 요리를 처리합니다. |

서버의 기존 `handlers_guild_cooking.go`는 가입 수렵단 범위로 완성 결과를
저장·반환하므로 이 동선에 맞습니다. 특별방이라고 성공 결과를 더 높이거나
재료·티켓을 서버에서 다시 빼지 않습니다. 공유 보관 음식의 기본 60분과
`ClanMealDuration` 운영 설정도 그대로 유지합니다. 요리를 다시 조회한다고
보관 시각을 갱신하지 않습니다. 요리 스킬의 효과·지속시간은 별도 클라이언트
처리이므로 보관함 만료와 혼동하지 않습니다.

실제 서버 누락은 요리 생성 SQL에서 발견했습니다. `guild_meals.guild_id`는
integer, 가입 테이블은 bigint인데 동일한 `$1`을 `INSERT SELECT`와 가입
검사에 사용해 PostgreSQL 자료형 추론이 충돌할 수 있었습니다. 생성 쿼리의
출력만 `$1::integer`로 명시해 정상 등록을 복구했습니다. 가입 검사와
다른 수렵단 보관함을 수정하지 못하는 제한은 그대로입니다.

## 수렵단 티켓 교환은 선율 교환과 별개입니다

공식 매뉴얼은 `チケット交換`의 추가 품목과 `歌迎特別アイテム交換`을
서로 다른 특전으로 열거합니다. [공식 PlayStation 안내](https://blog.ja.playstation.com/2016/11/04/20161104-mhfz/)도
추가 티켓 교환과 외장 교환을 구분합니다.

서버의 `ENUMERATE_SHOP type 9`는 **선율**을 쓰는 76종 교환이며 수렵단 티켓
상점이 아닙니다. 티켓 추가 품목을 이 목록에 섞거나 가짜 서버 상점 유형을
추가하지 않았습니다. 기존 수렵단 티켓 상점의 정확한 전체 구매 동선·목록은
이번 분석에서 끝까지 확정하지 못했으므로, 실제 특별방에서 메뉴를 확인해야
합니다. 티켓 교환까지 새 서버 기능으로 구현 완료했다고 분류하지 않습니다.

## 추가한 회귀 테스트와 실제 게임 확인

`diva_special_cooking_test.go`는 저랭크 수렵단의 등록·덮어쓰기,
결과 0~3의 원형 보존, 재조회 시 만료 시각 보존, 기존 운영 보관시간을 검증합니다.
이 테스트는 서버 ACK의 검증이며 화면과 미니게임 자체를 실행한 검증은 아닙니다.
`repo_diva_special_cooking_test.go`는 별도 로컬 테스트 DB에서 정상 생성,
다른 단원의 동일 보관함 덮어쓰기, 탈퇴 이후 변경 거절을 확인합니다.

운영자가 확인할 항목:

1. 특별방에서 요리 시설이 열리는지 확인합니다. 가능하면 일반방에서 요리가
   잠기는 저랭크 수렵단으로도 확인합니다.
2. 같은 메뉴·재료·보조 옵션에서 일반방과 특별방의 대성공 판정 영역을 비교합니다.
   특별방에서도 실패/일반 성공은 가능해야 합니다.
3. 요리 후 다른 단원이 보관 음식을 먹을 수 있는지, 다시 열거나 재접속해도
   보관 시간이 새로 시작하지 않는지 확인합니다.
4. 수렵단 상점의 **티켓 교환**에서 특별 품목이 표시되고 티켓으로 정상 교환되는지
   확인합니다. 선율 76종 메뉴와 혼동하지 않습니다. 비어 있다면 메뉴 화면과
   그 시각의 패킷 로그로 클라이언트 목록인지 서버 조회인지 먼저 확정합니다.
