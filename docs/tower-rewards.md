# 천랑원정록 보수·정보 근거 (2026-09-25)

자동 로테이션은 포함하지 않았습니다. 운영 설정은 EarthStatus 21,
EarthID 1입니다. 기록은 EarthID별로 분리합니다.

## 원본으로 확인한 내용

- 운영자가 제공한 12페이지 인게임 조사보수 스크린샷에서 1~500층의
  115개 항목을 전사하여 이전 25개 표를 교체했습니다. 화면의 개최
  회차는 알려지지 않았으므로 특정 회차의 공식 표라고 단정하지
  않습니다. 아이템 ID는 Ferias sozai/item.js와 대조했습니다.
  40층의 흐린 품목은 운영자가 제시한 Ferias ID 2A3D와 과거
  천랑 보수 자료를 대조해 앵성철(桜星鉄) 3개로 확정했습니다.
- [네실 천랑원정록 위키](https://w.atwiki.jp/giurasu/pages/1175.html):
  일일보수는 하루 여섯 과제, 일본 시각 낮 12시 갱신입니다.
  완료한 보수는 개최 보수 수령 기간 동안 보관됩니다. 과제 종류는
  층수, 몬스터 토벌, 보물상자, 고보품, TRP 등이 있습니다.
- [몬스터 헌터 사전 위키](https://wikiwiki.jp/nenaiko/%E3%82%B7%E3%82%B9%E3%83%86%E3%83%A0/%E5%A4%A9%E5%BB%8A%E9%81%A0%E5%BE%81%E9%8C%B2):
  선행공헌보수는 캐주얼 모드 해금 전에 수문장을 토벌했을 때
  개최당 한 번 받습니다. 기존 1·2·3·5회 토벌 단계는 제거했습니다.
- 운영자가 제공한 인게임 가이드: 조사보수는 층수 기준,
  선행공헌은 수문장 토벌, 일일교체보수는 지정 과제 달성 기준입니다.

## 구현과 추론의 경계

- 조사보수 유형 260003은 스크린샷의 층수·수량을 기준으로 한
  115항목을 표시합니다.
  선행공헌 유형 260001은 단일 항목이며, 품목인 청아의 고문서 1개는
  원본 미확보 서버용 대체품입니다.
- 완료한 퀘스트당 1~4층을 회차 진행도로 한 번 적립합니다.
  보물상자·고보품·몬스터 수치는 종료 보고에서 추가합니다.
  수렵단에 없어도 개인 층수와 일일 기록은 남습니다.
- 일일 과제 여섯 개는 낮 12시에 회전합니다. 과제 종류는
  원본 자료에 근거하지만 목표 수치, 품목·수량 및 일부 패킷 필드는
  서버용 추론입니다. 달성 기록은 날짜별로 보관합니다.
- 천랑 정보의 구역별 수문장 토벌 수는 파티당 한 번 계산합니다.
  몬스터·소재 공개용 고정 가짜 수치 5771/1847은 제거했습니다.
  완료 층수당 100점을 주는 서버용 탐사 점수를 보냅니다.
  클라이언트의 기존 몬스터·소재 공개 조건에 연결하려는
  추론값이며, 원본 증가율은 아직 모릅니다.
- 공헌 보수(보수 유형 260003·260001)는 `MSG_MHF_PRESENT_BOX` 세 동작을
  씁니다(ZZ 클라이언트 `Mazetower::mt_PresentCommunicator` 분석, D431).
  - 1번(목록): 창을 열 때와 수령 중에 보냅니다. `Unk3` 는 페이지 오프셋이고
    44바이트 행을 버퍼 ACK 로 돌려줍니다. 오프셋이 목록 끝을 넘으면 빈 목록입니다.
  - 3번(개수): 창을 열 때 1번과 함께 보내는 **수령 가능 개수 조회**입니다.
    단순 ACK 값으로 개수를 돌려주며, 257개 이상이면 창이 안내 문구를 띄웁니다.
    예전 구현은 3번을 수령으로 처리해 창을 여는 순간 보수를 창고의
    꺼내기 전용 상자(item10)에 넣고 영수증을 남겼습니다. 그 때문에 수령
    단계의 목록이 비어 '공헌 보수 수령'이 아무 반응이 없었습니다.
  - 2번(수령): 클라이언트가 공간이 있는 행을 **직접 소지품에 넣은 뒤** 그 행들의
    인덱스(`Unk2` 개수, `Unk7`)를 보내고 세이브 업로드를 함께 합니다. 서버는
    영수증만 남기고 아이템을 따로 지급하지 않습니다. 응답은 단순 ACK 입니다.
    버퍼 ACK 를 보내면 클라이언트가 오류 0x12 로 수령을 실패 처리합니다.
    그 뒤 오프셋 +0x100 으로 1번을 다시 요청하고, 빈 목록이 오면 끝냅니다.

## 인게임 확인이 필요한 사항

- 일일 보수 유형 260002는 추론입니다(천랑 보수 창은 260003·260001만 요청).
  2번 요청의 인덱스 위치(`Unk7`)와 3번이 개수 조회라는 점은 클라이언트
  코드로 확인했습니다. 실제 수령 결과창은 인게임 확인이 필요합니다.
- 여섯 과제 행이 원하는 문구·목표로 보이는지, 탐사 점수가
  몬스터·소재 물음표를 실제로 해제하는지 테스트해야 합니다.
  현재 단계에서 완전한 원본 재현이라고 주장하지 않습니다.
- 같은 날 일일 보수 화면을 연 시간대에 `MSG_MHF_GET_PAPER_DATA`
  `DataType=4` 요청이 있었지만, 이 요청은 다른 구역 로딩 시에도
  `GET_RENGOKU_BINARY`와 함께 반복됩니다. 일일 화면 전용이라고
  단정할 수 없습니다. 현재 4번은 빈 응답이며, 여섯 과제와
  12시~익일 12시 시간표는 0번으로 전송된 것을 로그에서 확인했습니다.
  기존 클라이언트 메모리 덤프의 일일 미션 수신 함수는
  `4 + 시간표수×8 + 과제수×10` 바이트를 검사하며, 현재 0번 응답의
  길이·행 구조는 이 검사와 일치합니다. 이 함수가 과제 첫 바이트를
  1부터 시작하는 시간표 번호로 사용하고, 한 시간표에 최대 여섯 과제를
  연결하는 것도 확인했습니다. 기존 서버는 이 값을 과제 칸 번호 1~6으로
  잘못 보냈으므로, 현재 시간표 1번으로 모두 수정했습니다. 실제 화면에
  여섯 과제와 남은 시간이 표시되는지는 재검증해야 합니다. 임의의
  4번 행은 전송하지 않습니다.
- 선행공헌 원본 품목·수량, 일일 과제의 개최별 원본 표,
  수렵단 조사 보수 원본 표는 확보하지 못했습니다. 수렵단 보수는
  기존 서버용 대체표를 유지합니다.

테스트용으로 운영 DB에서 asdf 캐릭터 56의 EarthID 1 층수를
0에서 1로 올렸습니다. 이전 tower.block1은 NULL이었고 다른
천랑 스탯은 변경하지 않았습니다. 테스트 뒤 되돌리기 전에는
그사이의 실제 진행·수령 이력을 확인해야 합니다.

## 2026-09-26 보강: 조사 이력·일일 보수 진행도 (vorbis.dll D425/D426)

- **일일 과제 종류 번호 정정**: 과제 행의 두 번째 바이트는 클라이언트의
  과제 문구 표 번호입니다(G10.1 `[pac+0xd94]`, ZZ `[pac+0xde0]`, 한국어
  번역 포함): 1 답파 계층수, 2 TRP 획득, 3 보물상자, 4 고보품,
  5 대형 몬스터 토벌, 6~9 제1~4구역 파수꾼 토벌. 이전 풀은 길드
  미션(천랑위래) 번호를 써서 "500 TRP" 과제가 "대형 몬스터 500마리"로
  보였습니다. 또 클라이언트는 TRP 목표를 100배해서 쓰므로(ZZ
  `FUN_113ac8d0`) 500 TRP 는 목표값 5 로 보냅니다. 보수 판정
  `towerDailyMissionMet` 도 같은 번호로 서버 일일 카운터를 읽습니다.
- **일일 진행도 저장(TINY_BIN 0/1/1)**: 클라이언트는 여섯 과제의
  진행도를 스스로 누적해(퀘스트 종료 `FUN_10b1d450`) 32바이트
  `[시간표 종료, 진행 6개, 달성 비트]`로 `MSG_MHF_POST_TINY_BIN`
  0/1/1/1 에 올리고, 로그인 때 `MSG_MHF_GET_TINY_BIN` 0/1/1 로
  받습니다(길이가 0x20 이 아니면 0으로 초기화). 이전 서버는 저장하지
  않아 재접속마다 진행도가 사라졌습니다. 새 표 `tower_daily_bins`
  (0066)에 그대로 보관합니다. 표시용 값이며 보수 지급은 여전히
  서버 카운터로 판정합니다.
- **조사 이력(GET_TOWER_INFO InfoType 4)**: 기본 정보 페이지의
  【조사 이력】①~⑤는 Earth 값 1001(현재 회차)부터 거꾸로 다섯 회차를
  이력 항목의 회차 번호와 맞춰 층수를 보여 줍니다(G10.1
  `FUN_104b0d80`). Earth 값 1001 을 EarthID(미설정이면 이전 값 36)로,
  이력은 `tower_event_progress` 의 회차별 1·2구역 층수 합으로 보냅니다.
  ZZ 클라이언트는 1001 을 읽지 않고 vorbis.dll 의 기본 정보 페이지만
  사용합니다.
- 일일 보수 화면(타워 스테이터스 3페이지)은 ZZ 에서 삭제되어
  vorbis.dll 이 G10.1 `FUN_105dc590`/`FUN_105dbe90` 배치로 다시
  그립니다. 과제·보수·목표·현재값·남은 시간·달성 도장은 위 데이터를
  씁니다.


## 2026-10-25 정정: 일일 보수 보관·수령 구현

일일 보수는 위의 추론 유형 `PRESENT_BOX 260002`를 쓰지 않는다. 실제 HD·비HD
언팩본에서 확인한 별도 `TINY_BIN 0/1/2` 보관함을 사용한다.

- 달성 판정: HD `10b1d450`, 비HD `10aff9e0`. 완료 도장은 과제 달성 비트이며
  소지품 수령을 뜻하지 않는다. 이미 완료된 과제는 다시 보수 목록에 넣지 않는다.
- 퀘스트 종료: HD `10b77d20`, 비HD `10b59db0`가
  `PostDoubleTinyBinCommunicator`로 진행 `POST 0/1/1/1`과 새 보수
  `POST 0/1/2/3`을 보낸다. 보수 행은 리틀엔디언 `uint16 아이템 ID, uint16 수량`이다.
- 기존 Erupe는 진행만 저장하고 보수 요청은 무시한 채 성공 응답했다.
  이제 진행의 새 달성 비트와 서버가 보낸 해당 날짜 과제 표를 대조하고,
  두 요청이 일치하면 진행과 보수 보관을 같은 DB 트랜잭션으로 확정한다.
  DB 실패 때는 실패 ACK를 보내며 진행 완료만 먼저 남기지 않는다.
- 새 `0095_tower_daily_rewards.sql`은 과제·보수 칸별 고유 기록과 미수령 행을 보관한다.
  동일 요청 재전송·동시 처리로 보수가 중복 생성되지 않는다.
- 접수원 일일 보수 수령: HD `10387060`이 `GET 0/1/2`로 보관 목록을 받고,
  공간이 있는 아이템을 클라이언트 소지품에 직접 넣는다. 목록은 255행으로 제한한다
  (요청 버퍼 0x400바이트, 수령 화면의 행 수는 1바이트).
- 전부 받으면 `POST 0/1/2/2`, 일부만 받으면 남은 행을 `POST 0/1/2/1`로 보낸다.
  받은 행의 수령 확정은 함께 오는 인증된 클라이언트 `SAVEDATA`와 원자적으로 처리한다.
  서버가 별도 창고에 아이템을 추가하지 않는다. 공간 부족 행과 조회 후 추가된 행은 유지한다.
- 추론 `PRESENT_BOX 260002` 지급은 제거하여 같은 과제를 다른 경로로 이중 지급하지 않는다.
- 과거 완료 비트의 미지급분을 조회·변환·소급 지급하지 않는다. 사용자 요청대로 복구는 제외한다.
  마이그레이션은 새 빈 표만 만들며 운영 DB·서버에는 적용하지 않았다.

검증은 정식 회귀 테스트와 운영 DB와 분리된 PostgreSQL 스키마에서 수행한다.
HD·비HD 모두 같은 네이티브 패킷을 사용하며 30/60fps에 따른 서버 경로 차이는 없다.
DLL 변경이나 배포는 필요하지 않다. 실제 게임 수령 확인은 새 서버 적용 후 필요하다.

검증 결과(2026-10-25): 천랑·보수·관련 세이브 선택 회귀 154건(하위 사례 포함),
실제 PostgreSQL 실패 주입·동시 재전송·수령/세이브 롤백 및 `-race` 검사 통과, 건너뜀 0.
서버 실행 파일 빌드도 통과했다. 전체 채널 서버 테스트는 다른 기능의
5433 포트 고정 요구와 `TestChannelIsolation_ShutdownDoesNotAffectOthers`의
