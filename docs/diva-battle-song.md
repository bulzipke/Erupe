# 전가의 장: 노래 발동

2026-09-22. 서버만 수정하며 클라이언트 코드·메모리·Vorbis는 변경하지 않는다.
대상은 ZZ의 `GET_REWARD_SONG`, `USE_REWARD_SONG`, `ADD_REWARD_SONG_COUNT`이다.

## 클라이언트에서 확인한 형식

분석 대상: `mhfo-hd.dll.clean.mapped.bin`.

| 함수 | 확인 내용 |
| --- | --- |
| `114fdfc0`, `11535c80` | GET은 22바이트 버퍼: `u8 error`, `u8 used`, `u32 activation_id`, `u32 activated_at`, 4개의 `u16 effect_id + u8 used_count` |
| `103a0ce0`, `103b2300` | 남은 횟수는 달성한 전역 목표 개수에서 GET의 used를 뺀다. GET의 0은 **이미 사용한 횟수 0**이지 남은 횟수 0이 아니다. |
| `103a0c30` | 남은 효과 시간은 `activated_at - client_now + 3600`이다. 종료 시각을 보내면 1시간이 추가되는 오류가 생긴다. |
| `114fe0d0`, `11536890` | USE는 1바이트 **버퍼형 ACK**를 읽는다. 기존 simple ACK는 올바른 응답이 아니었다. |
| `114fe1e0`, `11535e80` | ADD는 activation ID와 효과 ID 목록을 전송한다. 이름과 달리 노래 발동 기회를 추가하는 패킷이 아니라 제한형 효과의 소비 보고다. |
| `103a0c50`, `103b2300` | 효과 ID를 찾아 해당 소비 횟수를 읽는다. 효과 목록의 배열 위치가 기주의 색상과 같을 필요는 없다. |
| `1039d8f0`, `103a0bc0`, `103a0fa0` | 효과의 레벨은 날짜별 우승 기주와 클라이언트 최대 레벨표를 사용한다. 효과 설명은 GET 노래 패킷의 문자열이 아니다. |

ADD 호출은 전투 종료 후의 경로에서 확인했다:
`10899d90` 상태 2 → `1089be10/10b742c0` 종료 판정 → 상태 3 `1089c780`
→ 상태 5 `1089cb50` → `10aff970` 내부 `10affc78` → `11535e80`.
로비 이동 패킷과 정확히 어느 쪽이 먼저 오는지는 확정하지 못했으므로 출발 스냅샷은
마을 복귀 후에도 유지하고, 다음 실제 출발에서만 교체한다.

## 구현

- 기도 단계에서 해당 회차에 기주를 선택하고 1점 이상 기여한 캐릭터만 발동 가능하다.
- 전가 단계의 실제 시작·종료 시각을 검증한다. 강제 기도·가영, 비활성 상태에서는 거절한다.
- 기존 전역 목표 `udMilestones`를 클라이언트와 동일하게 센다. 낮은 인원수 때문에 임계치를 낮추거나,
  스케줄의 `0x19`만 보고 무료 25회를 지급하지 않는다.
- 1회 사용 시 캐릭터·회차별 소비 횟수, 새 발동 ID, 발동 시작 시각을 저장한다.
  활성 중 중복 사용은 성공 응답하되 추가로 차감하거나 1시간을 연장하지 않는다.
- DB 캐릭터 행 잠금으로 채널 간 동시 요청을 직렬화하고, 잠금 획득 후 DB 시각으로 기간을 다시 확인한다.
- 재접속·서버 재시작 시 같은 상태를 반환한다. 새로운 회차의 소비 내역은 별도로 시작한다.
- 발동 시 기주 효과 ID들을 고정하고 제한형 효과 소비 횟수를 별도로 저장한다.
  검증된 퀘스트 출발 시 서버 UUID·회차·발동 ID·출발 시각을 연결한다.
  ADD는 이 출발과 일치하는 효과만 각각 1회 소비하며, 같은 출발의 동일 보고는 중복 소비하지 않는다.
- 노래가 끝난 뒤 퀘스트에서 돌아오더라도 실제 출발 때 유효했던 발동에 대한 소비는 기록한다.
  새 노래가 이미 발동된 경우 이전 ID의 신규 보고로 새 상태를 차감하지 않는다.
- `InGameTimeOverrideHour`는 클라이언트 시계만 이동시키므로 노래 발동·소비를 거절한다.

사용횟수 상한표의 첫 조건은 현재 **서버 누적 500,000점**, 13개 조건이다.
이 표가 40회 원본 전체와 일치한다는 근거는 아직 없다. 이번 변경은 표를 유지한다.
따라서 기도 참여 기록이 없는 강제 전가 회차나 전역 첫 목표를 달성하지 않은 회차는
수정 후에도 남은 횟수 0이 맞다. 임의로 누적치·우승 기주를 생성하지 않는다.

## 원본 자료와 미확정 범위

- [공식 최종 매뉴얼](https://web.archive.org/web/20191218054658id_/http://cog-members.mhf-z.jp/sp/manual/page399.html):
  기도 단계의 참여와 전체 노래 구슬에 따른 횟수, 날짜별 기주 집계, 전가 단계의 발동 구조를 확인했다.
- [당시 플레이 자료 정리](https://w.atwiki.jp/giurasu/pages/1392.html):
  1회 노래의 지속 시간은 1시간이며, 폭풍 기주는 **노래 1회당** 제한형 퀘스트 횟수를 가진다.
  이는 새 발동에서 효과 소비 횟수를 초기화하는 규칙을 뒷받침하지만 40회 서버 패킷 원본은 아니다.

효과의 종류·수치·최대 레벨·유효한 퀘스트 예외는 클라이언트 기존 계산을 유지한다.
서버는 효과가 실제 전투 중 발생했는지 독립적으로 시뮬레이션하지 않는다.
ADD 원본 패킷에는 퀘스트 ID/서버 UUID가 없으므로, **다음 출발 이후 같은 발동 ID로 과거의 보고를
새 요청처럼 보내는 조작까지 완전히 구별할 수는 없다.** 현재 멱등성은 서버가 연결한 출발 범위의
재전송을 대상으로 하며, 완전한 클라이언트 조작 방지 기능이라고 주장하지 않는다.
효과 소비를 보고하지 않는 변조 클라이언트까지 강제 검증하는 것은 이번 범위가 아니다.

기도 보수, 요격 지도·에리어, 요격 보너스 퀘스트, 선율 교환은 별개 기능이다.

## 검증 기록

- 전체 `go build ./...` 및 변경 패키지 `go vet` 통과.
- 격리 PostgreSQL(`127.0.0.1:5433`, `erupe_test`)에서 노래 발동·소모,
  기존 디바 보수·랭킹·퀘스트 이동을 `-race`로 검증했다.
  하위 테스트 포함 1,929개 통과, Windows 심볼릭 링크 권한이 필요한 기존 테스트 1개만 건너뛰었다.
- 새 스키마의 재적용, 횟수·영수증 보존, 값 범위, 캐릭터/회차 삭제 연동 테스트 통과.
  전체 신규 설치 및 이미 적용된 DB 재시작 마이그레이션 테스트도 통과했다.
- `schema_version` 자체를 유실한 기존 DB의 전체 복구 테스트는 이번 변경 이전의
  `0034_raviente_runs.sql`에서 테이블 중복 생성으로 실패했다. 새 `0053` 도달 전이며
  이 별도 문제의 코드는 변경하지 않았다.
- 운영 DB 변경, 배포 및 실제 게임의 발동 화면·전투 효과 확인은 수행하지 않았다.
