## 지도 조회 응답

ACK 바깥 헤더를 제외한 본문입니다. 정수는 모두 big-endian입니다.

```text
u8 error
if error == 0:
    u8 definition_count
    definition[definition_count]
    u16 treasure_row_count
    treasure_row[treasure_row_count]
    u8 state_count
    state[state_count]
    u32 acquired_area_count
```

nonzero error면 나머지를 읽지 않습니다. 성공 시 모든 카운트와 마지막 합계가 필요합니다.
파서는 카운트 범위를 검사하지 않으므로 서버에서 제한해야 합니다.

| 배열 | 클라이언트 용량 | 서버 제한 |
|---|---:|---:|
| 지도 정의 | 8 (`0x3840 / 0x708`) | 최대 8 |
| 정의별 노드 | 64 | 정확히 64개 직렬화, 미사용 0 |
| 보물 목록 | 512 (`0x2000 / 0x10`) | 최대 512 |
| 지도 상태 | 2 (`0xe10 / 0x708`) | 최대 2 |
| 상태별 노드 | 메모리 64, 화면 60 | 유효 노드 최대 60 |

### 지도 정의

```text
u32 template_id
u32 linked_template_id
node_definition[64]  // 각 23바이트
```

두 번째 ID는 다음 템플릿 ID 방향으로 쓰입니다. `103b97b0`은 `linked_template_id == current_id`인
정의를 찾고 해당 정의의 ID로 역추적하여 이전 페이지의 존재를 계산합니다.
단일 정의가 자기 자신을 가리키면 `map_number - 1`을 사용하므로 반복 지도 표현이 가능합니다.
복수 정의의 원본 순환 구성과 지도 번호 정책은 아직 미확정입니다.
`103b97b0`의 역추적은 횟수 8에서 제한되므로 복수 템플릿 순환이 바로 무한 루프가 되는 것은
아닙니다. 다만 이전 페이지 수를 잘못 산출할 수 있어 현재 인코더는 비순환 연결 및 끝의
단일 자기 링크만 허용하고 두 개 이상의 템플릿을 거치는 순환은 거절합니다.

| 노드 wire offset | 형식 | 확인된 의미 |
|---:|---|---|
| 0 | u16 | 좌표 ID |
| 2,4,6,8,10 | u16 × 5 | 파싱 확인. 조사한 HD 화면 소비 경로에서는 읽지 않음 |
| 12 | u8 | 파싱 확인. 조사한 HD 화면 소비 경로에서는 읽지 않음 |
| 13 | u8 | 종류. 1: 시작, 2: 목표, 3: 분기점 |
| 14 | u32 | 기본 필요 포인트. 상태 필요 포인트와 비교해 추가분 계산 |
| 18 | u8 | 내부 u32로 확장. nonzero면 일반 보물 목록 표시를 건너뜀 |
| 19 | u32 | 보물 그룹 ID |

좌표 ID는 `행 * 100 + 열`입니다. 화면은 `row=5-id/100`, `column=id%100-1`입니다.
유효 범위는 `101..112`, `201..212`, `301..312`, `401..412`, `501..512`입니다.

### 보물 목록

각 행은 14바이트입니다.

| wire offset | 형식 | 의미 |
|---:|---|---|
| 0 | u32 | 그룹 ID: 정의 offset 19와 비교 |
| 4 | u8 | 보수 종류. 이번 확인: 7=아이템, 26=GP. 전체 열거값은 미확정 |
| 5 | u16 | 보수 ID로 전달 |
| 7 | u16 | 보수 수량으로 전달 |
| 9 | u16 | 적용 지도 번호 하한(포함) |
| 11 | u16 | 적용 지도 번호 상한(포함) |
| 13 | u8 | `>1` 여부로 보물 표시 구분 |

현재 지도 번호가 모든 상한보다 크면 해당 그룹의 최대 상한 행을 재사용합니다.
형식 확인만으로 미확보 원본 보물 보수를 채우면 안 됩니다. 승인된 대체 보물은 분기별
아이템 1026×5와 GP 500이며 원본 보물표라고 주장하지 않습니다. `107a3c20`의 selector 2는
`ACQUIRE_UD_ITEM` 종류 5를 사용하고, `107a3b70`의 지급 경로에서 ItemType 7/26을 확인했습니다.

### 지도 진행 상태

```text
u32 template_id
u16 map_number
u8 node_count
node_state[node_count]  // 각 23바이트
```

상태 0은 현재 지도, 상태 1은 비교/이전 지도 화면에 사용됩니다(`103a90b0`).

| wire offset | 형식 | 확인된 의미 |
|---:|---|---|
| 0 | u32 | 해당 노드에 반영한 획득 포인트 |
| 4 | u32 | 해당 노드 필요 포인트 |
| 8 | u16 | 좌표 ID: 정의와 연결 |
| 10 | u16 | 다음 진행 노드 좌표 ID. 메인 및 분기 경로에서 사용 |
| 12 | u16 | 분기 시작 노드 좌표 ID. 분기가 없으면 0 |
| 14,16,18 | u16 × 3 | 해당 분기 퀘스트 ID |
| 20 | u8 | 화면 노드 순번. 1..60 범위 안에서 1부터 연속이어야 함 |
| 21,22 | u8 × 2 | 파싱 확인. 조사한 HD 화면 소비 경로에서는 읽지 않음 |

`103b9440`은 `max(required-earned,0)`을 남은 포인트로 계산합니다.
`103b8bd0`은 목표 노드가 `earned>=required`이면 완료로 판단합니다.
`103b99c0`은 분기 해금 상태에 따라 최대 3개 퀘스트 ID를 추출합니다.
연결 추적 경로 중에는 null 검사가 없으므로 없는 노드 연결·중복 좌표·범위 밖 순번은 위험합니다.
원본 연결 관계는 미확보입니다. 운영 코드는 사용자 승인된 단일 반복 템플릿·메인 20개·
단일 노드 분기 2개로 제한하며, 이를 원본 지도라고 취급하지 않습니다.

분기 연결의 방향은 추가 분석으로 정정했습니다. 분기점 J에 대하여 `state.next == J`인 P를
찾아 P의 획득 여부를 확인하고, `state(J).branch_start`에서 분기를 시작합니다.
그 뒤에는 분기 노드의 `next`를 따라갑니다(`103b8ac0`, `103b99c0`).
따라서 wire offset 10을 이전 노드 ID로 보내면 분기 해금 조건이 뒤집힙니다.

마지막 u32는 `DAT_1e827480`에 저장되며 지도 제목·요약의 획득 에리어 합계입니다.
개인/수렵단 요격 포인트를 그대로 넣어서는 안 됩니다.

## 추가 소비 경로 분석 및 최소 표현 조건

미확정 필드에 대해 첫 노드의 실제 저장 주소를 조회했습니다.
정의의 `1e820e3a/3c/3e/40/42/44`와 상태의 `1e82467f/680`에는 파서 쓰기 참조만 있으며,
지도 검색 결과를 화면용 40바이트 노드로 바꾸는 `103b9440`도 이 필드를 복사하지 않습니다.
현재 HD의 조사한 조회·표시 경로에서는 0으로 둘 수 있습니다. 다만 다른 버전이나
아직 조사하지 않은 간접 사용까지 없다는 보장은 아니며 원래 필드의 업무상 이름은 미확정입니다.

분기·보물 없는 메인 경로의 최초 최소 표현 조건은 다음과 같습니다.
이는 일반 프로토콜 설명이며, 이후 승인된 분기/보물 확장은 아래 운영 연결 절에 따릅니다.

1. 템플릿 ID는 1..65535, 중복 없이 전송합니다. `103b8a40`이 조회 ID를 16비트로 마스킹합니다.
2. 상태의 템플릿 ID는 반드시 정의에서 찾을 수 있어야 합니다. 지도 번호는 1 이상입니다.
3. 시작(type 1), 0개 이상의 일반 노드(type 0), 목표(type 2)를 하나의 순서로 표현합니다.
   노드 좌표는 고유해야 하며 위의 5 × 12 범위 안이어야 합니다.
4. 순번은 시작부터 `1..N` 연속입니다. `103a4db0`은 순번 배열의 첫 NULL에서 반환하므로
   순번 공백 뒤의 노드는 표시·진행 게이지 처리에서 누락됩니다.
5. offset 10은 다음 노드, 마지막 목표의 next는 0입니다. main-only에서는 offset 12와
   3개 분기 퀘스트 ID 모두 0이며 정의에 type 3 분기점을 두지 않습니다.
6. 시작의 필요/획득 점수는 0, 획득 대상 노드의 필요 점수는 양수여야 합니다.
   특히 목표가 required=0이면 처음부터 완료로 판단하여 지도 생성 루프를 유발합니다.
   앞쪽 완료 노드, 미완료 최전선, 뒤쪽 미획득 노드의 점수 상태를 일관되게 만듭니다.
7. 보물이 없으면 보물 행 count=0, 정의의 보물 그룹 ID=0입니다.
   `11536390`은 이 카운트를 읽기 전에 보물 배열을 `memset(..., 0, 0x2000)`하므로
   0개 응답은 이전 응답의 보물 캐시를 유지하지 않습니다.
8. 미사용 정의 노드는 64개 고정 슬롯의 나머지를 0으로 채웁니다. 유효 상태 노드는 최대 60입니다.
9. 단일 템플릿 자기 링크와 map_number>1 조합은 이전 페이지 UI를 켭니다.
   이 경우 이전 지도 상태도 두 번째 상태로 제공해야 합니다. 첫 지도는 map_number=1입니다.
10. 목표 획득 뒤 GENERATE 성공 시 실제 새 상태로 전환되어야 합니다. 빈 성공이나 무변경 성공은 금지합니다.

위 조건은 정적 코드 분석으로 확인한 서버 인코더 검증 기준입니다.
이러한 본문을 실제 실행 중인 클라이언트에 전송해 화면을 검증한 것은 아닙니다.

추가 안전 제한으로 필요/획득 포인트와 획득 에리어 합계는 signed UI 연산 범위인
`0..2147483647` 안이어야 합니다. 상태 필요 포인트는 정의의 기본 필요 포인트 이상이어야
추가분 계산이 음수/언더플로가 되지 않습니다. 인코더는 좌표의 5 × 12 범위와 연결의
유효성·진행 순서는 검사하지만 연결된 두 좌표의 기하학적 인접 여부까지 보장하지 않습니다.
2026-09-23 추가 분석에서 홀수 열이 반 칸 아래로 내려가는 육각 이웃과 현재/직전 두 페이지
전환을 확인했습니다. [추가 조사](diva-map-randomization-research.md)에 함수·좌표식을 기록했습니다.
이후 `custom-random-v2` 생성기와 기하학 테스트에 적용했습니다. 범용 wire 인코더와 기존 v1의
배치를 소급해서 기하학 규칙으로 거절하지는 않습니다. 실제 게임 표시 검증은 별도로 필요합니다.
`diva_interception_map_protocol_test.go`의 지도와 수치는 프로토콜 검사용 가상 fixture이며
원본 데이터나 운영용 대체 지도는 아닙니다. 인코더는 현재 검증된 `custom-v1` 운영 handler에
연결돼 있지만, wire 단위 테스트를 실제 인게임 화면 검증으로 간주하지 않습니다.

## 현재 구현된 진행 계산과 운영 연결

`diva_interception_map_progress.go`는 검증된 메인 경로의 미완료 지점부터 입력 점수를
차감하는 순수 계산입니다. 임계값에 정확히 도달해도 획득 처리하며, 이미 완료한 노드는
다시 세지 않습니다. 시작점은 제외하고 목표까지의 초과 점수는 폐기합니다. 결과는 입력과
중첩 슬라이스까지 분리하며, 이전 지도 상태는 변경하지 않습니다.

`diva_custom_map.go`와 `repo_diva_map.go`는 승인된 별도 대체표를 출발 스냅샷/개인 결과
저장 트랜잭션에 연결합니다. 메인 20개에 분기 2개를 더하고, 메인 5·15개 완료 후 해금합니다.
분기 기본 5,000점은 메인과 같은 지도 배율을 적용합니다. 개인 점수는 별도로 유지하며,
서버가 저장한 지도·회차·분기 원장을 UTC+9 매시 정각에 정산합니다.

- 0054 cutover 이후 새로 시작한 실제 요격 회차만 대상이며 과거/설치 당시 진행 중 회차는 격리합니다.
- 수렵단·회차·지도·출발 UUID로 저장하여 재전송, 동시 정산, 재시작에서 이중 반영하지 않습니다.
- 획득 에리어 원장을 04·12·20시 스냅샷으로 고정하며, 동률 1·1·3은 승인된 대체 규칙입니다.
- 분기 기여자별 종류 5 보물, 기존 직접 6/추론 6행의 종류 7 달성 보수 수령을 연결했습니다.
- 특별방은 1에리어/가영 기간/현재 회원에 따라 INFO_GUILD 플래그를 반환합니다.
  실제 입장 성공과 선율 교환 완성을 의미하지 않으며 선율은 여전히 미구현입니다.

지원되는 회차의 조회·생성 handler와 에리어 랭킹은 실제 저장 상태를 전송합니다. 비대상 회차,
데이터 오류 등의 지도 조회·생성은 buffer ACK 성공 본문 `01`로 종료합니다. 에리어 랭킹의
빈 응답과 구별해야 합니다. 이전 `ff` 실패 응답은 재조회 루프를 일으켰으므로 안전한 실패가
아니었습니다. 단위·격리 DB race 테스트는
통과했지만 **실제 게임 화면·지도 전환·보물 수령·특별방 입장은 미검증**입니다.
실서버 DB 변경·배포·클라이언트 패치는 하지 않았습니다.

## 생성 및 귀환 처리

GENERATE 응답은 ACK 성공 본문 안의 u8 error입니다.
조회 결과 0xf7이면 귀환 처리기가 생성을 요청합니다.
유효 노드가 없거나 목표 노드를 획득한 경우에도 생성 후 다시 조회합니다.
빈 지도를 성공으로 반환하거나 상태 변화 없이 생성 성공만 반환하면 재요청 루프가 생길 수 있습니다.
생성은 수렵단·회차 기준으로 멱등적이어야 하며 데이터 부족을 정상 지도로 위장하면 안 됩니다.

### 오류 응답 정정: `ff`는 종료가 아닌 재조회

2026-09-23 실제 반복 요청 로그와 `103a8a80`/`103a97f0`를 대조했습니다. 지도 메뉴의
`103a8a80` case 3(GET) 및 case 5(GENERATE)는 본문 `ff`를 받으면 state 6/7로 이동하여
`GET_UD_INFO`를 다시 요청합니다. 이후 state 1로 돌아가 남은 에리어와 지도를 재조회합니다.
따라서 차단된 회차나 DB 오류에 `ff`를 계속 보내면 로딩 창과 요청이 반복됩니다.

| 응답 | 지도 메뉴의 다음 동작 |
|---|---|
| buffer ACK 성공 + 본문 `ff` | 이벤트 정보 → 남은 에리어 → 지도 재조회 |
| GET의 transport ACK 실패 또는 잘못된 simple ACK | GENERATE 요청 시도 |
| GET의 본문 `f7` | GENERATE 요청 |
| GET 성공, 유효 노드 없음/목표 획득 완료 | GENERATE 요청 |
| GENERATE 본문 `00` | 지도 재조회 |
| buffer ACK 성공 + 본문 `01` | 기존 오류 안내창을 띄우고 사용자 확인 대기 |

`115367d0`는 transport 실패를 status 3으로, 본문 오류는 status 1과 해당 오류 바이트로
구분합니다. `01`의 원작 업무상 명칭은 미확정이지만 메뉴의 종료 분기는 확인했습니다.
`103a97f0`는 실패 반환 1을 받아 state `0xB`에서 리소스 `+0x11c4`의 오류 안내를 표시하고,
state `0xC`에서 확인 입력을 기다립니다. 대기 중 네트워크 재요청이 없고, 확인하면
state `0xA` → 반환 0 → 상위 `107bcbd0`가 지도 화면을 닫습니다.

현재 handler는 이용 불가·검증 실패·새 지도로 전환할 수 없는 GENERATE에 `01`을 사용합니다.
이는 지도를 표시하거나 현재 회차를 활성화하는 처리가 아닙니다. cutover 정책 변경과
오류 응답 수정은 별개입니다. 회귀 테스트는 해당 네이티브 분기를 옮긴 작은 상태 모델로
`ff`/transport 실패/빈 성공과 종료 응답을 구별하며, 실제 클라이언트 실행 검증을 대신하지 않습니다.

## 특별 수렵단방까지 남은 에리어

요청 opcode 0x187 본문(`11500930`): `u32 ack_handle, u32 guild_id, u32 value_28, u32 zero`.
상수 28의 운영상 의미는 미확정입니다.
응답은 error 바이트 없이 u32 하나입니다(`115375c0`).
`103a7e40`이 특별 수렵단방까지 남은 에리어 문구에 사용하므로 일반 포인트로 해석하면 안 됩니다.
현재 handler는 1에리어 기준으로 남은 수 1 또는 0을 반환합니다. 0은 에리어 조건 충족이며,
기도/전가 중 조기 입장 권한을 의미하지 않습니다. 가영 기간의 INFO_GUILD 정보 플래그는
별도 자격 검사로 계산합니다. 기존 stage 입장 서버 경로에는 특별방 전용 권한 검사가 없고,
정상 클라이언트가 그 플래그를 소비해 실제 입장하는지는 실게임 검증이 남아 있습니다.

## 원본 규칙 및 미확보 데이터

[서비스 종료 직전 공식 매뉴얼](https://web.archive.org/web/20191218054658id_/http://cog-members.mhf-z.jp/sp/manual/page399.html)의 요격전 항목에 근거합니다.

- 지도·에리어 획득은 약 1시간 간격으로 갱신됩니다.
- 에리어마다 필요 포인트가 다릅니다.
- 현재 지도 몬스터 점거지를 모두 획득하면 다음 갱신 때 새 지도로 이동합니다.
- 잔여 포인트를 새 지도 에리어 획득에 넘기지 않습니다.
- 분기 퀘스트 포인트는 개인 점수에는 포함하지만 메인 경로에는 합산하지 않습니다.
- 다음 지도 이동 후 이전 지도 분기 에리어를 획득할 수 없습니다.
- 수렵단 랭킹은 획득 에리어 수 기준, 04시·12시·20시에 갱신됩니다.

미확보 데이터는 회차별 지도 템플릿·연결 순서, 모든 노드의 기본 필요 포인트·지도별 증가량,
분기 해금 연결·퀘스트 배정표, 보물 종류·수량·조건, 미확정 wire 필드 의미입니다.
임의의 `N점=1에리어` 변환은 원본 지도·랭킹·수렵단 보상을 모두 바꿉니다.
전송 프로토콜 복원과 40회차 지도 복원은 구분해야 합니다.
