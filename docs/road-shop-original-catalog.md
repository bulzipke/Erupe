# 수련도(狩煉道) 포인트 교환: 원본 복원 조사

> **2026-10-03 정정:** 내장 표는 탭 0~6의 889행뿐이다. 탭 7·8에는
> 내장 상품이 없으므로, 9/21에 모든 추가 목록을 지운 상태는 제한·초특수
> 상점의 원본 복원을 완료한 상태가 아니었다. 현재 복원은 아래 추가 조사와
> `seed/RoadShopItems.sql`의 **61행**을 따른다(1차 59행 + 라이브 외장권 2행).
> 같은 날의 최종 품목 재대조 결과는 문서 맨 아래에 기록했다. 과거의 일괄 제거 SQL을 다시
> 실행하면 새 복원 상품도 사라진다. 아래 9/21 내용은 당시 기록으로 보존한다.

조사일: 2026-09-21. 대상: 일본 MHF-ZZ 최종 서비스 시기의 수련도 교환.
사용자는 기존 편의용 판매품을 유지하지 않고 원본 목록으로 교체하는 방향을 선택했다.
복원 방법은 제3자 표 950행을 DB에 삽입하는 것이 아니라, 서버의 편의용
추가/덮어쓰기 목록을 제거해 **ZZ 클라이언트 내장 원본 목록**을 사용하게 하는 것이다.
최종 2019년 전체 품목의 수치와 주간 초기화까지 모두 검증했다는 뜻은 아니다.

## 클라이언트에서 확인한 원본 목록 경로

Ghidra 대상: `mhfo-hd.dll.clean.mapped.bin`. 정적 분석이며 클라이언트는 수정하지 않았다.

| 함수 | 확인한 역할 |
| --- | --- |
| `FUN_101d1ff0` / `FUN_101d4480` | 수련도 NPC 및 교환 상점 진입 |
| `FUN_104029c0`, case `0xC` | 내장 수련도 표 포인터를 상점 데이터에 설정 |
| `FUN_10403e50` | 서버 type10 목록을 먼저 넣고 내장 표를 병합; 서버에 같은 아이템이 있으면 내장 항목 생략 |
| `FUN_11528af0` | 0행 응답도 정상 성공으로 처리 |
| `FUN_11528fe0` | 목록 요청 Limit512; 추가 필터/페이지 필드는 0 |

따라서 서버 0행은 교환소 전체가 비었다는 뜻이 아니다. **서버에서 추가하거나
덮어쓰는 항목이 0개**이고, 이후 내장 표만 사용한다. 내장 표의 개별 가격·한도와
주간 초기화 로직은 이번에 전수 추출하지 않았으므로 별도의 검증 범위로 남긴다.

`FUN_104fc630` / `FUN_10584d10`의 제작소 경로는 서버의 여러 카테고리 목록을
합쳐 512칸 배열에 복사한다. 단순히 탭당 제한을 풀고 950행을 서버 추가 목록으로
넣는 것은 원본 복원 방법도 아니며 안전성도 확인되지 않았다.

## 근거의 구분

- 공식 공지/매뉴얼의 보존본: 직접 확인한 내용만 공식 근거로 사용한다.
- 당시 인게임 화면: 화면에 보이는 조건·수량·페이지 범위만 확인된 것으로 친다.
- Ferias: 원본 게임의 교환 정보를 보존한 유용한 제3자 자료다.
  모든 값이 공식 최종 목록과 완전히 일치한다고 단정하지 않는다.
- Erupe seed/현재 DB: 현재 서버의 설정이며 원본을 입증하는 출처가 아니다.

## 공식 공지와 블로그/Ferias 사이의 불일치

[공식 공지 13639 보존본](https://web.archive.org/web/20191218002242/http://cog-members.mhf-z.jp/sp/news/13639.html)은
2018-12-26 추가된 외장 해방권을 확인할 수 있는 근거다.
다만 추가 품목 공지와 가격·진행도·한도 전체표는 구분해야 한다.
[당시 정리글](https://byuwasoku.hatenablog.com/entry/2019/01/09/120644)은 7품목을
각 1,000P / 교환 가능 수5로 정리하지만, 다음 두 품목의 진행도가 Ferias와 다르다.

| 아이템 | ID | 당시 블로그 | Ferias |
| --- | --- | ---: | ---: |
| ボニト解放券Ｄ | 3861 | 100 | 110 |
| メイリダ解放券Ｄ | 3862 | 110 | 100 |

날짜 차이에 따른 사양 변경인지 전사 오류인지는 미확정이다.
1차 복원에서는 이 조건 차이 때문에 두 품목을 보류했다. 이후 사용자의
라이브 품목 누락 없는 복원 요청에 따라, 존재가 공식적으로 확인된 두 품목을
당시 블로그의 조건으로 추가했다. 조건의 출처 상충은 해결됐다고 가장하지 않는다.

또한 `0x3FD5 和戟の布`는 Ferias의 최고진도가 10이지만,
[추가 당시 기록(2019-02-28)](https://byuwasoku.hatenablog.com/entry/2019/02/28/115855)은
**최고진도50 / 주간46개**로 설명한다. 이후 완화 여부를 확인하기 전에는
Ferias의 10이나 현재 서버의 20을 최종 공식 값으로 확정하지 않는다.

## 공식 매뉴얼에서 확인한 조건

[공식 수련도 매뉴얼 보존본](https://web.archive.org/web/20170709025224/http://cog-members.mhf-z.jp/sp/manual/page432.html)
(2017-07-09 캡처, 초기 사양)의 설명을 직접 읽었다.

- 일반 교환에는 필요 GR와 최고진도가 있다. 최고진도는 정기점검마다 리셋되지 않는다.
- 횟수 제한 아이템의 한도는 정기점검 구간마다 적용된다.
- 초특수 아이템은 최고진도 대신 특정 몬스터 토벌 수를 요구한다.
  이 토벌 수는 평생 누계가 아니라 정기점검 구간 내 값이며, 교환 횟수 제한도 있다.

이 매뉴얼에는 전체 품목별 가격·GR·한도 표가 없으므로, 설명만으로
950개 행의 모든 필드를 채울 수는 없다.

## 서버 추가 목록과 원본 표를 구분해야 하는 이유

- 서버 추가 상품의 `shop_items_bought`에는 날짜/주차가 없고 `bought`만 누적한다.
  이 장부의 한계를 근거로 내장 원본 품목도 영구 제한이라고 단정할 수는 없다.
- `handlers_shop.go`의 type10 탭당 256행 상한은 서버 추가 목록에 대한 것이다.
  내장 G급 소재가 424행이라는 이유만으로 이 상한을 없앨 필요가 없다.
- 원본 표의 가격/조건을 재현하려고 서버 override를 다시 만들지 않는다.
  원본을 사용하는 동작과 모든 조건의 완벽한 서버 권위 검증은 별개다.

## 적용 및 복구 파일

- 신규 DB 기본 seed: `server/migrations/seed/RoadShopItems.sql`은 추가 상품을 넣지 않는다.
- 기존 DB: `server/migrations/manual/restore_native_road_shop.sql`을 운영자가 명시적으로 실행한다.
  자동 마이그레이션으로 전체 서버의 커스텀 상품을 지우지 않는다.
- 승인된 삭제 범위: `shop_type=10 AND shop_id BETWEEN 0 AND 8`.
- 같은 트랜잭션에서 `road_shop_overrides_backup_20260921` 테이블로 원본 ID를 포함해 백업한다.
  백업이 이미 있으면 재실행은 실패하며 기존 백업을 덮어쓰지 않는다.
- 구매장부, 포인트, 인벤토리, 다른 상점, ID 시퀀스는 변경하지 않는다.
- 복구: `server/migrations/manual/undo_restore_native_road_shop.sql`.
  기존 ID나 상품에 새 변경이 있으면 중단하고, 충돌이 없으면 정확한 옛 행을 복원한다.
- 접속 중 클라이언트는 목록을 이미 캐시했을 수 있으므로 재로그인 후 확인한다.

### 적용 결과 (2026-09-21)

- 운영 DB `erupe`: 승인된 수련도 override **861행 → 0행**으로 변경 완료.
- `road_shop_overrides_backup_20260921`: **861행** 보존. 필요하면 위 복구 SQL로 되돌릴 수 있다.
- 다른 상점 79행: 변경 전후 행 내용 해시가 동일함을 트랜잭션 안에서 확인했다.
- ID 시퀀스의 `last_value`/`is_called`가 동일함을 확인 후 커밋했다.
- 포인트·인벤토리·구매장부에는 변경 명령을 실행하지 않았다.
- 새 기본 seed도 서버 추가 목록을 넣지 않도록 변경했다. 서버 재시작/배포는 하지 않았다.

### 검증

격리된 로컬 PostgreSQL에서 `TestRoadShopNativeCatalogRestore`를 `-race`로 실행해 통과했다.
신규 seed 0행, 백업/제거/정확한 복원, 반복 복원, 다른 상점 보존,
시퀀스/구매장부 보존, 기존 백업 덮어쓰기 거절, 변경된 ID/동일 상품의 새 ID와
충돌 시 복원 거절을 확인했다. 운영 DB의 자체 구매/인게임 표시 검증은 아직 하지 않았다.
재로그인 후 기본·G급·횟수 제한·초특수 탭과 가격/진도 조건을 확인하는 것이 다음 단계다.

전체 `go test -race ./server/migrations`에서는 기존
`TestMigrateExistingDBWithoutSchemaVersion`이 `0034_raviente_runs.sql` 재적용 중
`relation "raviente_runs" already exists`로 실패했다. 이 실패는 seed 적용 전이며,
이번 작업에서 해당 마이그레이션은 수정하지 않았다. 수련도 전용 테스트 통과와
전체 패키지 통과를 혼동하지 않는다.

## 추가 조사와 1차 보완 (2026-10-03, 59행 반영 당시)

사용자가 실제로 본 빈 상점과 클라이언트 쪽 D543 조사 결과를 대조했다.
`mhfdat.bin` +0xB2C 표의 16바이트 레코드를 끝까지 확인했을 때,
탭 0~8의 개수는 20/9/28/162/218/28/424/0/0이다. 원본 내장 행은 유지하고
서버에서 받아야 하는 행만 추가한다. 기존 편의용 861행은 복구하지 않는다.

| 서버 보완 대상 | 행 수 | 처리 |
| --- | ---: | --- |
| 장식품 | 3 | G급·괴호주 / G급·초무주 / G급·공온주 |
| 횟수 제한 | 45 | 라비엔테 소재, 수련도 무기·방어구 소재, 외장권, 책 등 |
| 초특수 | 11 | 조룡 소재 10종과 조룡 외장권 |
| 보류 | 2 | 보니토/메이리다 외장권: 진행도 100/110 상충 |

총 59행(아이템 종류 58개). 회휘원주의 두 가격·진도 행을 합치지 않는다.
전체 라이브 최종 서비스 목록이 완벽히 확정됐다는 뜻은 아니다.

  그대로 복사하지 않았으며, 두 당시 표에서 공통인 가시 50을 사용했다.
- 조룡 소재 상한은 [2017년 강화 합계표](https://blog.livedoor.jp/guild5_mhf/archives/71363111.html)와

- 공온주는 Ferias의 진도1 대신, [당시 교환주 정리](https://blog.livedoor.jp/salvare3260/archives/16117088.html)와

  Ferias/위키에 있는 진도10으로 이후 완화되었는지는 미확정으로 남긴다.

  단독 출처인 항목은 공식 전체 원장으로 독립 검증한 것은 아니다.

### 서버 동작

- `0072_road_shop_weekly_limits.sql`: 상품의 `road_weekly_limit`과 구매장부의
  `week_start`를 추가한다. 기존 상점의 구매 수량·캐릭터 저장 데이터는 바꾸지 않는다.
- 사용자가 선택한 주기는 **한국/일본 시간 월요일 0시**다. 라이브 수요일 정기점검
  대신 현재 서버의 다른 주간 기능과 맞춘 운영 정책이다.
- 주간 제한을 선택한 수련도 탭 7·8의 구매 횟수만 주차별로 계산한다.
  조회 시 지난 주차는 사용0회로 응답하고, 다음 구매가 새 주차의 횟수를 기록한다.
  재시작이나 별도 타이머가 필요 없으며 다른 상점·커스텀 상품은 누적 장부를 유지한다.
- 요격전 깃발 3종은 가희수위전 **전가의 장** 중에만 목록에 보인다.
  비활성·다른 장·상태 조회 실패 시 제외한다. 목록 제한을 적용하기 전에 걸러낸다.
- GR·최고진도·조룡 토벌수·구매상한은 원본 패킷 필드로 전달한다.
  포인트 차감/아이템 지급과 조룡 토벌수의 저장·주간 처리는 클라이언트 기존 구현을
  그대로 사용한다. 이번 변경을 완전한 서버 권위 구매 검증이나 조룡 카운터 복원으로
  설명하면 안 된다. 인게임 조건 판정·구매·주간 전환 실기 검증은 별도다.
- 신규 DB seed는 최종 재대조 후 61행을 보완한다. 동일 품목·진도·토벌수의 기존 행은 덮어쓰지 않는다.
  일반 탭을 서버 원장으로 다시 만들거나 기존 256행 안전 상한을 해제하지 않는다.

### 운영 적용/복구

운영 적용 전 격리 DB에서 카탈로그·반복 seed·기존 복구 SQL·구매 장부를 검증한다.
서버 코드 배포 후 주간 초기화와 한정 깃발 노출이 동작한다. DB 목록만 넣고
옛 서버를 계속 실행하면 새 주간 처리/한정 상품 필터는 적용되지 않는다.
실제 적용 결과는 아래에 별도로 기록한다.

### 이번 변경의 검증

운영 DB와 분리한 로컬 PostgreSQL에서 다음 테스트를 실행해 통과했다.

- `go test ./server/migrations -run 'TestRoadShop' -count=1 -v`:
  카탈로그 수량·가격 합계·조건, seed 재실행, 기존 복원 SQL 호환,
  이번 복구 SQL의 변경/구매 상품 거절과 반복 복구.
- `go test -vet=off ./server/channelserver -run
  'Test(RoadShop|RepoRoadShop|RepoShop|HandleMsgMhfEnumerateShop_Case10)' -count=1 -v`:
  기존 상점 동작, 단계별 깃발 노출, 패킷 제한 전 필터링,
  지난 주/레거시 구매 수량 초기화, 캐릭터별 분리, 비대상 상점 보존,
  16개 동시 구매의 정확한 합산, 지연 요청으로 주차가 역행하지 않는 처리.
- 최신 코드의 `go build` 성공. 검증용 실행 파일은 저장소 밖 임시 경로에만 생성했다.

Go 1.27의 기존 `diva_area_ranking_test.go:27` vet 경고 때문에 채널서버
테스트만 vet을 비활성화했다. 해당 테스트 코드는 수정하지 않았다.
이번 실행에는 `-race`를 사용하지 않았으며 전체 테스트/인게임 실기 검증
통과로 확대해서 해석하지 않는다.

## 라이브 기준 품목 재대조 (2026-10-03, 최종 61행)

사용자가 말한 원본은 클라이언트 내장 목록 자체가 아니라 **일본 라이브 서비스 당시의
실제 교환소 목록**이다. 공식 추가 공지·당시 게시물·보존 사전과 내장 표를 구분해 대조했다.

### 보류 품목의 처리와 남은 불확실성

[2018-12-26 공식 공지](https://web.archive.org/web/20191218002242/http://cog-members.mhf-z.jp/sp/news/13639.html)의
추가 품목 표에는 보니토·메이리다를 포함한 외장권 7종이 명시되어 있다.
두 품목이 라이브에 존재했는지는 미확정 사항이 아니다. 보류 이유는 **해금 진도**였다.
누락하지 않도록 두 품목을 복원하고, 날짜가 있는
[2019-01-09 당시 교환표](https://byuwasoku.hatenablog.com/entry/2019/01/09/120644)를
적용 조건의 근거로 채택했다.

| 품목 | 아이템 ID | 현재 적용 진도 | 당시 교환표 | Ferias | 가격 / 주간 한도 |
| --- | ---: | ---: | ---: | ---: | --- |
| 보니토 해방권D / ボニト解放券Ｄ | 14433 (0x3861) | 100 | 100 | 110 | 1,000P / 5개 |
| 메이리다 해방권D / メイリダ解放券Ｄ | 14434 (0x3862) | 110 | 110 | 100 | 1,000P / 5개 |

따라서 **보류로 빠져 있는 품목은 이제 없다**. 다만 최종 라이브에서 두 진도가
변경됐는지, 어느 자료가 전사 오류인지 확정한 것은 아니다.
기존 `和獄の絹`/`和戟の布`의 진도50은 당시 기록과
[PlayStation 공식 소개](https://blog.ja.playstation.com/?p=1081)의 진도50 안내를 유지한다.
Ferias의 진도10과의 차이는 품목 누락과 별개인 조건 상충이다.

공식 공지에 있는 2018-12-26~2019-01-09의 **2주분 임시 증량/동일 품목 2행 표시**는
영구 상품으로 추가하지 않는다. 요격전 깃발 3종도 기존처럼 전가의 장에서만 노출한다.
회휘원주의 진도20/4,000P와 진도40/2,000P 두 행은 서로 다른 정상 교환 기록으로 유지한다.
