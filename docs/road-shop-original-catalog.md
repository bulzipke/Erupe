# 수련도(狩煉道) 포인트 교환: 원본 복원 조사

조사일: 2026-09-21. 대상: 일본 MHF-ZZ 최종 서비스 시기의 수련도 교환.
사용자는 기존 편의용 판매품을 유지하지 않고 원본 목록으로 교체하는 방향을 선택했다.
복원 방법은 제3자 표 950행을 DB에 삽입하는 것이 아니라, 서버의 편의용
추가/덮어쓰기 목록을 제거해 **ZZ 클라이언트 내장 원본 목록**을 사용하게 하는 것이다.
최종 2019년 전체 품목의 수치와 주간 초기화까지 모두 검증했다는 뜻은 아니다.

## 클라이언트에서 확인한 원본 목록 경로

Ghidra 대상: `mhfo-hd.dll.clean.mapped.bin`. 정적 분석이며 클라이언트는 수정하지 않았다.

| 함수 | 확인한 역할 |
| --- | --- |
| `FUN_101d1ff0` / `FUN_101d4480` | 수련도 NPC 및 교환 상점 진입 |
| `FUN_104029c0`, case `0xC` | 내장 수련도 표 포인터를 상점 데이터에 설정 |
| `FUN_10403e50` | 서버 type10 목록을 먼저 넣고 내장 표를 병합; 서버에 같은 아이템이 있으면 내장 항목 생략 |
| `FUN_11528af0` | 0행 응답도 정상 성공으로 처리 |
| `FUN_11528fe0` | 목록 요청 Limit512; 추가 필터/페이지 필드는 0 |

따라서 서버 0행은 교환소 전체가 비었다는 뜻이 아니다. **서버에서 추가하거나
덮어쓰는 항목이 0개**이고, 이후 내장 표만 사용한다. 내장 표의 개별 가격·한도와
주간 초기화 로직은 이번에 전수 추출하지 않았으므로 별도의 검증 범위로 남긴다.

`FUN_104fc630` / `FUN_10584d10`의 제작소 경로는 서버의 여러 카테고리 목록을
합쳐 512칸 배열에 복사한다. 단순히 탭당 제한을 풀고 950행을 서버 추가 목록으로
넣는 것은 원본 복원 방법도 아니며 안전성도 확인되지 않았다.

## 근거의 구분

- 공식 공지/매뉴얼의 보존본: 직접 확인한 내용만 공식 근거로 사용한다.
- 당시 인게임 화면: 화면에 보이는 조건·수량·페이지 범위만 확인된 것으로 친다.
- Ferias: 원본 게임의 교환 정보를 보존한 유용한 제3자 자료다.
  모든 값이 공식 최종 목록과 완전히 일치한다고 단정하지 않는다.
- Erupe seed/현재 DB: 현재 서버의 설정이며 원본을 입증하는 출처가 아니다.

## Ferias에서 추출 가능한 목록

일본어 [other_sozai.js](https://ferias.life.coocan.jp/sozai/other_sozai.js)의
`Shop` 사전에서 각 아이템 값의 콤마 구분 토큰 중 `23`으로 시작하는 항목이
수련도 교환이다. 이름/ID는 [item.js](https://ferias.life.coocan.jp/sozai/item.js)와 대조한다.
두 일본어 파일은 CP932로 읽어야 한다.

로컬 번역본:
`\\bulzipkenas\appdata\swag\www\ferias\sozai\other_sozai.js` (UTF-8).
조사 시 SHA256: `CC349902AE48542B48141C1E311E3901EAA5190937957C2843EB22C6D6E2C36B`.

예: `3A5B: 23(最高進度11)(装飾品) 1000狩P`.
진행도 조건·카테고리·비용이 포함된다. 주간 구매 한도나 묶음 수량까지
이 문자열만으로 확정할 수는 없다. 원본의 전각 `HR１` 등을 정규화해야 한다.

## 공식 공지와 블로그/Ferias 사이의 불일치

[공식 공지 13639 보존본](https://web.archive.org/web/20191218002242/http://cog-members.mhf-z.jp/sp/news/13639.html)은
2018-12-26 추가된 외장 해방권을 확인할 수 있는 근거다.
다만 추가 품목 공지와 가격·진행도·한도 전체표는 구분해야 한다.
[당시 정리글](https://byuwasoku.hatenablog.com/entry/2019/01/09/120644)은 7품목을
각 1,000P / 교환 가능 수5로 정리하지만, 다음 두 품목의 진행도가 Ferias와 다르다.

| 아이템 | ID | 당시 블로그 | Ferias |
| --- | --- | ---: | ---: |
| ボニト解放券Ｄ | 3861 | 100 | 110 |
| メイリダ解放券Ｄ | 3862 | 110 | 100 |

날짜 차이에 따른 사양 변경인지 전사 오류인지는 미확정이다.
임의로 한쪽을 택해 운영 DB에 설치하지 않는다.

또한 `0x3FD5 和戟の布`는 Ferias의 최고진도가 10이지만,
[추가 당시 기록(2019-02-28)](https://byuwasoku.hatenablog.com/entry/2019/02/28/115855)은
**최고진도50 / 주간46개**로 설명한다. 이후 완화 여부를 확인하기 전에는
Ferias의 10이나 현재 서버의 20을 최종 공식 값으로 확정하지 않는다.

## 공식 매뉴얼에서 확인한 조건

[공식 수련도 매뉴얼 보존본](https://web.archive.org/web/20170709025224/http://cog-members.mhf-z.jp/sp/manual/page432.html)
(2017-07-09 캡처, 초기 사양)의 설명을 직접 읽었다.

- 일반 교환에는 필요 GR와 최고진도가 있다. 최고진도는 정기점검마다 리셋되지 않는다.
- 횟수 제한 아이템의 한도는 정기점검 구간마다 적용된다.
- 초특수 아이템은 최고진도 대신 특정 몬스터 토벌 수를 요구한다.
  이 토벌 수는 평생 누계가 아니라 정기점검 구간 내 값이며, 교환 횟수 제한도 있다.

이 매뉴얼에는 전체 품목별 가격·GR·한도 표가 없으므로, 설명만으로
950개 행의 모든 필드를 채울 수는 없다.

## 변경 전 운영 DB 점검

대상 `172.18.155.200:5432 / erupe`, `shop_type=10`.
개인 계정/인벤토리는 수정하거나 정리하지 않았다.

| 현재 shop_id | 현재 행 수 | max_quantity > 0 | road_fatalis > 0 |
| --- | ---: | ---: | ---: |
| 4 | 274 | 0 | 0 |
| 7 | 174 | 0 | 0 |
| 8 | 413 | 0 | 0 |
| 합계 | **861** | 0 | 0 |

서버 추가 목록에는 0·1·2·3·5·6 탭 데이터가 없다. 내장 품목의 부재를 뜻하지 않는다.
Ferias와 같은 `(탭, 아이템 ID)`는
6행만 확인됐고, 이 행들도 현재 진도20 / Ferias 진도10으로 다르다.
다른 탭에 같은 아이템이 있을 수 있으므로 '944종 모두 없는 아이템'으로 해석하지 않는다.
현재의 `スペリアチケット` 999개/1P, 비전 커프류 등은 원본 목록 근거와 별도로 취급한다.

## 서버 추가 목록과 원본 표를 구분해야 하는 이유

- 서버 추가 상품의 `shop_items_bought`에는 날짜/주차가 없고 `bought`만 누적한다.
  이 장부의 한계를 근거로 내장 원본 품목도 영구 제한이라고 단정할 수는 없다.
- `handlers_shop.go`의 type10 탭당 256행 상한은 서버 추가 목록에 대한 것이다.
  내장 G급 소재가 424행이라는 이유만으로 이 상한을 없앨 필요가 없다.
- 원본 표의 가격/조건을 재현하려고 서버 override를 다시 만들지 않는다.
  원본을 사용하는 동작과 모든 조건의 완벽한 서버 권위 검증은 별개다.

## 적용 및 복구 파일

- 신규 DB 기본 seed: `server/migrations/seed/RoadShopItems.sql`은 추가 상품을 넣지 않는다.
- 기존 DB: `server/migrations/manual/restore_native_road_shop.sql`을 운영자가 명시적으로 실행한다.
  자동 마이그레이션으로 전체 서버의 커스텀 상품을 지우지 않는다.
- 승인된 삭제 범위: `shop_type=10 AND shop_id BETWEEN 0 AND 8`.
- 같은 트랜잭션에서 `road_shop_overrides_backup_20260921` 테이블로 원본 ID를 포함해 백업한다.
  백업이 이미 있으면 재실행은 실패하며 기존 백업을 덮어쓰지 않는다.
- 구매장부, 포인트, 인벤토리, 다른 상점, ID 시퀀스는 변경하지 않는다.
- 복구: `server/migrations/manual/undo_restore_native_road_shop.sql`.
  기존 ID나 상품에 새 변경이 있으면 중단하고, 충돌이 없으면 정확한 옛 행을 복원한다.
- 접속 중 클라이언트는 목록을 이미 캐시했을 수 있으므로 재로그인 후 확인한다.

### 적용 결과 (2026-09-21)

- 운영 DB `erupe`: 승인된 수련도 override **861행 → 0행**으로 변경 완료.
- `road_shop_overrides_backup_20260921`: **861행** 보존. 필요하면 위 복구 SQL로 되돌릴 수 있다.
- 다른 상점 79행: 변경 전후 행 내용 해시가 동일함을 트랜잭션 안에서 확인했다.
- ID 시퀀스의 `last_value`/`is_called`가 동일함을 확인 후 커밋했다.
- 포인트·인벤토리·구매장부에는 변경 명령을 실행하지 않았다.
- 새 기본 seed도 서버 추가 목록을 넣지 않도록 변경했다. 서버 재시작/배포는 하지 않았다.

### 검증

격리된 로컬 PostgreSQL에서 `TestRoadShopNativeCatalogRestore`를 `-race`로 실행해 통과했다.
신규 seed 0행, 백업/제거/정확한 복원, 반복 복원, 다른 상점 보존,
시퀀스/구매장부 보존, 기존 백업 덮어쓰기 거절, 변경된 ID/동일 상품의 새 ID와
충돌 시 복원 거절을 확인했다. 운영 DB의 자체 구매/인게임 표시 검증은 아직 하지 않았다.
재로그인 후 기본·G급·횟수 제한·초특수 탭과 가격/진도 조건을 확인하는 것이 다음 단계다.

전체 `go test -race ./server/migrations`에서는 기존
`TestMigrateExistingDBWithoutSchemaVersion`이 `0034_raviente_runs.sql` 재적용 중
`relation "raviente_runs" already exists`로 실패했다. 이 실패는 seed 적용 전이며,
이번 작업에서 해당 마이그레이션은 수정하지 않았다. 수련도 전용 테스트 통과와
전체 패키지 통과를 혼동하지 않는다.
