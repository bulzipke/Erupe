# 가희 기주 보너스 타깃: 구현과 원본 자료

2026-09-21. 대상 클라이언트: ZZ / `mhfo-hd.dll.clean.mapped.bin`.

## 이번에 구현한 범위

기도의 장에서 **선택한 기주 색 + 타깃 조건 + 시간**이 맞을 때 적용되는
노래 구슬 보너스 목록 전송이다. `GetUdBonusQuestInfo`의 고정 빈 목록을 교체했다.
기주를 선택했다는 이유만으로 모든 사냥 점수에 상시 배율을 주지 않는다.
다음 단계인 전가의 장의 `祈歌` 전투 버프/사용 횟수 저장은 별도 미구현이다.

원본 40회 일정의 날짜별 대상·배율은 아직 확보하지 못했다.
**기본 설정은 빈 목록이며, 운영 설정/DB에 임의 배율이나 추론 일정을 넣지 않았다.**
따라서 코드 반영만으로 지금 보너스가 활성화되었다는 뜻은 아니다.
자료가 확보되면 아래 설정에 추가할 수 있도록 전송 기능과 검증을 구현한 상태다.
사용자가 별도로 요청한 랜덤 2배 편성은 아래 `DivaBonusRandom`으로 제공한다.
이것은 40회 원본 복원이 아니라 사용자 지정 운영 규칙이다.

## 랜덤 모드

```json
"GameplayOptions": {
  "DivaBonusRandom": true,
  "DivaBonusTargets": []
}
```

- UTC+9 **00·03·06·09·12·15·18·21시**를 경계로 3시간마다 바뀐다.
- 현재 노래 구슬 몬스터 목록을 회차별로 한 번 섞은 순환 목록으로 만들고, 4색의 시작 위치를
  `floor(색번호×몬스터 수/4)` 간격으로 벌린 뒤 각 구간마다 한 칸씩 이동한다(색번호 0~3).
  같은 구간의 네 색은 항상 서로 다른 몬스터다.
- **회차 전체 출현 횟수는 몬스터 간 최대 1회 차이**, 각 색 안의 횟수도 최대 1회 차이로 맞춘다.
  각 색은 모든 몬스터를 한 번 순회하기 전에는 같은 몬스터를 다시 받지 않는다.
  현재 후보 113마리/56~57구간에서는 **한 색 안의 중복이 0회**다.
  224행은 111마리가 2회·2마리가 1회, 228행은 111마리가 2회·2마리가 3회 등장한다.
  이는 출현 횟수 기준이며, 시작·종료에 잘린 짧은 구간까지 동일 시간으로 만들지는 않는다.
- 후보가 8마리 이상이면 바로 다음 구간에도 직전 네 마리가 다시 등장하지 않는다.
  후보가 4~7마리로 줄어도 균형·같은 구간 중복 금지를 유지하며, 연속 구간 사이에는
  수학적으로 피할 수 없는 최소 `8-후보 수`마리만 겹친다. 서로 다른 후보가 4마리 미만이면 거절한다.
- 모든 행은 `MultiplierPercent=200`, 즉 총 2배다.
- 실제 기도 기간은 **601,200초=6일 23시간**이다. 8일은 클라이언트 저장 버킷 수다.
  첫/마지막 구간은 실제 시작/종료에 맞춰 자르며, 이벤트 기간을 8일로 늘리지 않는다.
- 자정 시작이면 56구간×4색=224행(3,586바이트), 시작시각에 따라 최대 228행이다.
  320행 및 날짜·색별 10행 한도를 지킨다.
- 알고리즘 버전·회차 ID·저장된 시작시각·몬스터 ID의 SHA-256 순위로 순환 목록을 결정한다.
  슬롯 위치는 저장된 회차의 첫 3시간 구간부터 계산하며, 요청 시점이나 호출 순서에 좌우되지 않는다.
  같은 몬스터 목록에서는 채널/서버 재시작/재접속/재조회와 무관하게 동일하고, 회차가 바뀌면 다시 편성된다.
  몬스터 목록 자체를 바꾸는 업데이트는 진행 중 편성을 바꿀 수 있으므로 회차 중에는 피한다.
- **이번 균등 배정 변경을 배포하면 기존 독립 추첨 방식의 진행 중 회차도 일정이 한 번 바뀐다.**
  가능하면 회차 사이에 적용하고, 진행 중 적용한다면 서버 재시작 후 모든 클라이언트가 재로그인해
  새 전체 목록을 받도록 해야 한다. 기존 캐시를 서버에서 즉시 교체하는 푸시 기능은 없다.
- 기본값은 `false`. 수동 `DivaBonusTargets`와 동시에 설정하면 시작 시 오류다.
  ZZ 및 기주 4색이 필요하며, `InGameTimeOverrideHour`는 `null`이어야 한다.
- 운영 `config.json`은 이번 작업에서 수정하지 않았다. 적용 시 서버 재시작과 클라이언트 재로그인이 필요하다.

## 정확한 프로토콜과 적용 주체

`FUN_11534a40`의 응답은 big-endian `u16 count` 뒤에 다음 16바이트 행이 반복된다.

| 오프셋 | 형식 | 의미 |
| --- | --- | --- |
| 0 | u8 | 기주 색 슬롯, 1~4 |
| 1 | u8 | 조건 종류: 아래 1~7 |
| 2 | u32 | 대상 ID |
| 6 | u32 | 시작 Unix 초 |
| 10 | u32 | 종료 Unix 초, 포함 |
| 14 | u16 | 총 배율 퍼센트: 200=2배 |

기존 stub의 `StartTime, EndTime, Unk4, u8, u8` 추정은 잘못되어 있었다.
클라이언트 표시·판정 함수와 로컬 UI 원문을 대조해 7종 조건을 지원한다.

| TargetType | native kind | TargetID |
| --- | --- | --- |
| `rank` | 1 | 1=하위, 2=상위, 3=G급 |
| `field` | 2 | 아래 목적지 ID |
| `time_of_day` | 3 | 0=낮, 1=밤 |
| `monster_family` | 4 | 1=조룡, 2=비룡, 3=아수, 4=어룡, 5=갑각, 6=고룡, 7=수룡, 8=해룡, 9=아룡 |
| `monster` | 5 | 정규화된 몬스터 ID |
| `quest` | 6 | 퀘스트 ID |
| `monster_class` | 7 | 0=열종(烈種), 1=시종(始種), 2=천유종(遷悠種), 3=천이종(辿異種) |

랭크의 UI 문구는 HR2~4 / HR5~7 / GR1~이다. 실제 판정은 클라이언트의
하위/상위/G급 분기를 그대로 사용하며, 서버에서 별도 HR 하한을 추가하지 않는다.
특수종 ID 4~6은 원본에서 ID 3과 동일하므로 거절한다. 천이종 별 등급을 구분하는 값이 아니다.

필드 허용 ID는 `1..13,16,18,20,21,24,25,26,27,28,31,33,34,35,37,38,39,40,41,42,53..69`다.
주요 값은 2=숲과 언덕, 3=사막, 4=늪지, 5=화산, 6=밀림, 11=설산, 13=탑,
16=수해, 20=협곡, 28=절도, 31=고지, 35=조도, 37=극해, 40=꽃밭, 53=백호다.
`54..63`은 모두 원문명이 絶島地底이지만 서로 다른 판정 ID이므로 합치지 않는다.
별칭 `14/15/32→13,17→5,19/43→8,22→9,23→10,29/30→28,36→35`는 오른쪽 ID로 설정한다.
0 및 44~52는 dummy/공백 표시라 거절한다.

- `FUN_103a1cf0`: 선택 색·시간·대상을 검사하고 보너스를 계산한다.
- `FUN_103a27b0`: 별도 몬스터 집계 경로도 있다. 두 경로의 중복 조건 처리가 달라
  같은 색의 겹치는 일정은 설정에서 금지한다.
  **이 경로는 종류 4/5/7만 계산하며 1/2/3/6은 무시한다.** 목록에 표시된다는 것과
  모든 퀘스트에서 적용된다는 것은 다르다. `FUN_10ac3c70`의 퀘스트 +0x98 bit 0x80 및
  제외목록 분기를 유지하며, 서버에서 모든 퀘스트에 보너스를 강제하지 않는다.
- `FUN_103a1620` / `FUN_114fd490`: 타깃 추가분이 **이미 QuestPoints에 포함**되어 전송된다.
- `FUN_103a1fd0`: 별도의 BonusPoints는 권한 0x40, 즉 **Premium 코스 추가분**이다.
  기주 버프 추가분이라고 해석했던 패킷 주석을 수정했다.

서버는 전달받은 두 항목을 기존 트랜잭션으로 저장하며 배율을 다시 곱하지 않는다.
몬스터 랭크 보정, 부위파괴 가산, 복수 몬스터의 예외 처리를 서버에서 단순 곱셈으로
대체하지 않는다. 이는 클라이언트 신고 점수를 완전히 서버 권위로 검증하는 보안 기능은 아니다.

## 안전장치

- ZZ에서만 활성 설정을 허용한다. 다른 버전은 실제 분석 전까지 비어 있는 기존 응답을 유지한다.
- 기도 단계가 아니거나 이벤트 시작 전/종료 후에는 빈 목록을 보낸다.
- 최대 320행, 이벤트 시작일의 UTC+9 정오 기준 **8일 × 4색 × 각 10행**을 검사한다.
- 원본 파서와 같은 첫 번째 양끝 포함 정오 구간에 행을 배치해 개수를 센다.
  정확히 정오에 시작한 행이 이전 버킷에 들어가도 클라이언트가 모든 버킷을 검사하므로 정상이다.
- 정오를 가로지르는 일정도 허용한다. 불필요하게 분할하거나 1초 늦추지 않는다.
- 설정 종료는 미포함이며 wire에는 `종료 - 1초`로 보낸다. 인접 일정의 중복을 막는다.
- 같은 색의 시간 중첩, 음수/역전된 시간, 이벤트 범위를 벗어난 시간, Unix u32 넘침을 거절한다.
- 기주 목록이 1~3색뿐이면 존재하지 않는 색은 거절한다. 클라이언트는 미등록 색을
  첫 슬롯으로 돌릴 수 있으므로 단순 1~4 숫자 검사만으로는 부족하다.
- 배율은 100~10,000만 허용한다. 10,000은 운영상 안전 제한이며 원본 최고 배율이라는 뜻이 아니다.
- 잘못된 설정은 시작 시 거절하고, 이벤트/기주 조회 오류 및 날짜·색 버킷 초과에도 실패 ACK를 보낸다.
- 실제 노래 구슬 몬스터 목록에 없는 대상, 비어 있거나 없는 퀘스트 파일은 전송 시 실패 ACK와
  원인 로그를 남긴다. 점수 목록과 검증은 같은 몬스터 표를 사용하며 기존 기본 점수는 변경하지 않는다.
  퀘스트 파일 검사는 존재 여부만 확인하며 내용 유효성·수주 가능성까지 보증하지 않는다.
- `InGameTimeOverrideHour`는 클라이언트에 전달하는 Unix 시각 자체를 이동시키므로
  활성 보너스 목록과 동시 설정을 거절한다. 보너스 사용 시 `null`로 둔다.
- 모든 색과 전체 이벤트 일정을 함께 보내므로 색 변경·자정·재접속마다 일정을 새로 추첨하지 않는다.

## 설정 형식

`GameplayOptions.DivaBonusTargets` 기본값은 `[]`이다.
다음은 **동작 설명용 예시일 뿐 40회 복원값이 아니다. 운영 설정에는 적용하지 않았다.**

```json
"DivaBonusTargets": [
  {
    "Color": 4,
    "TargetType": "monster",
    "TargetID": 111,
    "StartOffsetSeconds": 72000,
    "EndOffsetSeconds": 86400,
    "MultiplierPercent": 200
  }
]
```

뜻: 이벤트 기도 단계 시작 **20시간 후부터 24시간이 되기 전까지** 노랑 슬롯의 미도가론을
총 2배 대상으로 지정한다. 20:00~24:00이라는 시각으로 읽어서는 안 된다.
이벤트 시작이 자정일 때만 그 시각과 일치한다. `DivaOverride=1`에서도 저장된 시작점을 사용한다.

몬스터 ID 범위는 1~176이며 클라이언트 정규화 별칭 `60→54, 155→147,
163→159, 172→170, 174→122`는 오른쪽 ID로 설정해야 한다. 이 범위 안에서도 서버의
노래 구슬 목록에 없는 소형 몬스터 등은 거절한다.
퀘스트 ID는 1~65,535다. 반드시 서버에 실제로 존재하는 퀘스트를 사용한다.
특히 **40,000 이상 이벤트 퀘스트는 클라이언트가 실제 이벤트 목록으로 받아야
보너스 메뉴에 표시된다**. 이 옵션이 미배포 퀘스트를 자동으로 공개하지는 않는다.

설정을 추가/변경한 경우 서버 재시작 및 클라이언트 재로그인이 필요하다.

## 확인된 한계와 별도 후속 작업

- 기도 종료/강제 회차 갱신을 가로질러 늦게 도착한 점수의 귀속 문제는 남아 있다.
  AddUdPoint에 이벤트 ID·퀘스트 ID·클라이언트 정산 시각이 없고 현재 구현은 신고 시점의
  이벤트를 사용한다. 퀘스트 출발/일정 재조회/정산 패킷 순서를 실제로 확인한 뒤 보완해야 한다.
  이번 타깃 조건 확장에서는 이벤트 수명주기와 지연 신고 정책을 임의로 변경하지 않았다.
- 같은 회차 중 서버 설정을 변경하면 기존 접속 클라이언트의 캐시와 달라질 수 있다.
  기간 중 변경은 피하고, 변경 시 재로그인이 필요하다. 서버가 클라이언트 캐시의 버전을
  확인하거나 기존 신고 점수에서 적용 조건을 역산하는 기능은 없다.
- 전가의 장 전투 기도 효과, 보수 목록/수령 이력 복원은 타깃 목록과 별개다.
  이 작업을 가희 전체 기능 완료라고 해석하면 안 된다.

추가 분석 근거: `FUN_103b0ef0`(UI), `DAT_118649c0`(필드 표), `FUN_10b4c510`(필드 정규화),
`FUN_10b4c3e0`(주야), `FUN_103a9df0`(종족), `FUN_1039ead0`(특수종),
`FUN_1087b5c0/1087b590/10ac3450`(랭크). 문구는 로컬 mhfpac 원문 배열도 대조했다.

## 40회 및 과거 자료

[최종 공식 매뉴얼](https://web.archive.org/web/20191218054658id_/http://cog-members.mhf-z.jp/sp/manual/page399.html)은
색별 기간 한정 보너스 타깃이 최대 하루 3회 지정됨을 설명한다.
기주 선택, 정오의 승자 판정, 전가 단계의 전투 효과는 별도 시스템이다.
공식 예외로 복수 몬스터 중 한 종이 타깃인 퀘스트에서 양쪽을 사냥하면 양쪽에

## 검증 상태

기주/가희/보너스/관련 패킷 테스트를 `-race`로 실행해 통과했다.
색 누락·정오 경계·버킷 초과·종료 미포함 변환·200 인코딩·재접속·DB 오류·배율 중복 방지를 검증한다.
7종 조건/ID·파일 누락·255/256/320행 u16 count·320행 5,122바이트·321행 거절·3색 240행·
실제 스케줄 응답과 보너스의 시작점 일치도 검증한다. 재접속/앵커 검사는 mock 기반이며
운영 DB 재시작·클라이언트 계산 결과까지 검증했다는 뜻은 아니다.
균등 순환 배정은 후보 수 4~176 각각에 대해 전체/색별 출현 횟수 차이, 같은 구간 중복 금지,
연속 구간의 최소 중복, 후보 부족 거절, 카탈로그 순서·중복 행·다른 요청 순서에 대한 재현성을 검사했다.
현재 실제 카탈로그의 56·57구간 전체 균형 및 한 색 안의 중복 0회도 집중 `-race` 테스트로 확인했다.
인게임 활성 일정 테스트와 클라이언트 표시 검증은 아직 하지 않았다.
전체 패키지 테스트에서는 이번에 수정하지 않은 course 명령 테스트 4개와
라비엔테 `TestOperateRegisterIgnoresKilledTimeBeforeStart`가 실패한다.
