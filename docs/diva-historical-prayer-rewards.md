# 기도 보수: 과거 회차 자료 보완 (2026-09-22)

후속: [블로그 단일 임계점 5행 보완](diva-blog-reward-audit.md)과
[클라이언트 로테이션 형식 재현](diva-norma-rotation-analysis.md)을 추가했다.
현재 GR은 기존 20,000점 6행에 역사 보완 5행을 더한 11행이다. 아래의 6행/18행
실험은 추가 전 상태의 기록이다. 후속 서버 구현에서는 이 11행을 보존하고
103,000점부터 1,000점마다 백은결정/황금결정 각 5개를 번갈아 지급한다.
이는 40회 원본이 아닌 운영 대체안이며, [반복 보수 적용 내용](diva-norma-rotation-analysis.md#서버-구현-적용-2026-09-22)을 참고한다.
후속 [HR 반복 운영표](diva-hr-prayer-rotation.md)는 기존 일회 보수를 보존한 채
21,000점 이후 조약돌/GP 반복 지급과 이에 맞는 마지막 페이지 표시를 추가한다.

40회 원본 전체 복원이 아니다. 사용자의 과거 회차 자료 활용 요청에 따라,
화면에서 직접 확인한 GR 개인 달성 보수 한 단계를 추가했다.
기존 40회 GR 매일 보수·개인 랭킹 보수는 변경하지 않았다.

## 프로토콜과 수령

- ZZ `11535320`: u16 개수 + 각 19바이트(종류/ID/수량, GR, 상한/하한,
  점수 u32, 마지막 u8). 마지막 바이트는 0으로 유지한다.
- `103b6bd0`, `11925150`의 메뉴→보수 매핑: 개인 달성은 type 1,
  매일 0, 개인 랭킹 2, 수렵단 랭킹 3. 다른 카테고리로 재활용하지 않는다.
- 기도 진행 중에도 해당 회차 journal 점수 20,000 이상, GR1 이상이면
  수령 가능하다. 구 누적치를 새 회차에 소급하지 않는다.
- 기존 DB 영수증과 저장 트랜잭션에 연결: 회차/캐릭터/항목별 중복 지급 방지,
  GP와 아이템은 각각 대응하는 클라이언트 저장 성공 시 확정한다.
- 클라이언트 수정, 운영 DB 직접 지급, 배포는 하지 않았다.

## 원본 미확보 항목과 조사 결과

- HR2–4 / HR5–7 매일 보수: 해당 탭의 날짜별 품목과 수량 자료 미확보.
- 수렵단 랭킹 **보수**: 품목 개요는 있지만 순위 구간별 수량 자료 미확보.
  수렵단 **순위 집계/표시**는 이미 구현되어 있다. 제출 시점 수렵단에 귀속한
  노래 구슬을 회차별 합산하고 집계 시각과 기도 종료 시각을 적용한다.
  과거 기록 중 수렵단 스냅샷이 없는 행은 현재 소속에 임의 귀속하지 않는다.
- 수렵단 랭킹 보수와 요격전 수렵단 에리어 달성 보수는 서로 다른 시스템이다.
  에리어 보수표를 랭킹 보수로 전용하지 않는다.
- 조사 범위: 초기 1·3회/진설 1·2회 요약, 2017년 5월 개인 달성 화면,
  2017년 6월 순위 기록, 2019년 후기 회차 자료, 공식 매뉴얼 아카이브.

사용자는 미확보 항목에 대해 **원본과 구분한 대체 보수표를 먼저 검토**하기로
선택했고, 이후 제안한 표의 적용을 승인했다. 아래 대체 표는 코드에 반영했다.
운영 배포나 DB 직접 변경은 하지 않았다.

## 승인된 대체 보수 — 코드 적용 (2026-09-22)

아래는 역사 자료의 복원이 아닌 서버 운영안이다. 확인된 40회 GR 보수는
유지하며, 없는 HR 매일 보수와 수렵단 랭킹 보수만 채운다.
원본 대비 동등한 밸런스라고 주장하지 않는다.

| 참여 일수 | HR2–4 | HR5–7 |
| --- | --- | --- |
| 1일 | 기도의 조약돌 1 | 기도의 조약돌 2 |
| 2일 | 길드 공헌 포인트 100 | 길드 공헌 포인트 200 |
| 3일 | 혼옥 3 | 혼옥 5 |
| 4일 | 기도의 조약돌 1 | 기도의 조약돌 2 |
| 5일 | 길드 공헌 포인트 200 | 길드 공헌 포인트 400 |
| 6일 | 혼옥 5 | 혼옥 10 |
| 7일 | 기도의 조약돌 3 | 기도의 조약돌 5 |

기간 합계: HR2–4는 조약돌 5·혼옥 8·GP 300,
HR5–7은 조약돌 9·혼옥 15·GP 600. 참여 일수는 해당 회차에
노래 구슬을 얻은 날 수이며 연속 접속 일수가 아니다.
승급해서 동일 일차 HR/GR 보수를 중복 수령하지 않도록 일차별 공통 수령
그룹을 DB에 저장한다. 최초 수령 가능 목록 요청 시 해당 일차의 구간을 고정한다.
이미 발급된 보수 묶음은 승급 후에도 미수령 항목을 그대로 받을 수 있지만,
같은 일차의 다른 HR/GR 보수 묶음을 추가로 받지는 못한다.
기존 GR 발급/수령 기록도 0049 마이그레이션에서 일차별 그룹으로 보존한다.

| 기도 노래 구슬 수렵단 최종 순위 | 단원 1인당 회차 보수 |
| --- | --- |
| 1–100위 | 수렵단 티켓 50 + 이벤트 보조권 5 |
| 101–500위 | 수렵단 티켓 25 + 이벤트 보조권 2 |
| 501위 이하/미참여 | 없음 |

순위 구간 1–100/101–500과 수량은 승인된 운영 대체안이다. 요격 에리어 랭킹이 아니다.
기도 종료 후 확정 순위와 소속을 고정하고 해당 수렵단에 노래 구슬 기여 기록이
있는 단원을 대상으로 한다. 길드 이동으로 여러 순위 보수를 중복 수령할 수
없다. 이 조건도 원작 확정 규칙이 아닌 승인된 대체 규칙이다.

### 안전 장치와 적용 시점

- 0049는 수렵단 소속 변경 이력을 기록한다. **업데이트 설치 이전에 이미
  종료된 회차의 소속은 추측해서 복원하지 않으므로 그 회차 랭킹 보수는 미지급**이다.
  설치 당시 진행 중이고 종료가 아직 남은 회차부터 종료 시점 소속을 확인할 수 있다.
- 기도 종료와 기존 집계 대기시간(65분) 이후 순위 전체를 한 번 확정한다.
  이후 수렵단 해산이나 점수의 사후 변경으로 이미 확정한 순위를 바꾸지 않는다.
- 기도 종료 직전 소속 수렵단에 해당 회차의 양수 기여 기록이 있어야 한다.
  종료 후 탈퇴·이동해도 원래 자격은 유지되며 새 소속의 보수는 추가되지 않는다.
- `DivaOverride=1`은 기도 고정 모드이므로 개인/수렵단 랭킹 보수를 주지 않는다.
- 수령 방식은 기존 영수증·소재/GP 저장 트랜잭션을 사용한다. 클라이언트 수정 불필요.
- HR 내부 값은 2–99 / 100–999로 구분하고 GR>0인 캐릭터는 HR 보수에서 제외한다.
  ZZ `103b5570`의 탭 필터와 `10badde0`/`11858bea`의 99/100 경계를 대조했다.
- 소재 ID: 혼옥 0x1D2C, 기도의 조약돌 0x3694, 수렵단 티켓 0x0402,
  이벤트 보조권 0x069B. Ferias `sozai/item.js` 일본어 항목과 대조했다.

## 2026-09-22 실기 피드백: 아직 해결되지 않은 개인 달성 표시

GR 개인 달성 화면의 `20000 이후, 0마다`는 올바른 안내가 아니다.
ZZ `103b5ec0`의 `103b6509..103b655b`는 개인 달성 메뉴의 마지막 페이지를
반복 보수 안내로 표시한다. 첫 행의 기준점과 두 번째 행의 기준점 차이를
출력하며, 기존 GR 6행은 모두 20000이므로 간격이 0이 된다.
이 출력 분기에는 19번째 바이트를 검사하는 조건이 없다. 따라서 그 바이트만
바꾸는 것으로 해결했다고 해서는 안 된다. 바이너리 형식 테스트 통과는
네이티브 화면의 의미까지 검증한 것이 아니었다.

실제 서버 지급은 여전히 GR 20000점에서 6항목을 회차당 한 번 지급한다.
0점 간격으로 반복 지급하는 코드는 없다. 표시만 맞추려고 가짜 아이템,
도달 불가능한 기준점, 임의 반복 보수를 추가하지 않았다. 이 표시 문제는
**미해결**이다. 원본 마지막 페이지/응답 구성을 확보해 표시와 지급을 대조해야
한다. 마지막 페이지의 반복 문구만으로 원래 지급도 무한 반복이었다고
단정하지 않는다. 이번 작업은 클라이언트를 변경하지 않았다.

추가 어셈블리 확인: Ghidra가 함수로 인식하지 못했던 `1039def0`는 마지막
바이트 배열 `1e8183d4`를 읽는다. `103b57cd`/`103b580b`는 이를 반복 그룹
페이지 분리에 사용한다. 앞선 '아무 데서도 읽지 않는다'는 설명은 잘못이었다.
다만 마지막 페이지를 반복 안내로 그리는 조건 자체는 그대로이므로, 0/1만
바꿔 정상적인 유한 보수 목록이 된다고 결론내릴 수 없다. 현재 유한 보수는 0이다.

사용자는 HR 기도/요격 개인 달성 대체표를 검토한 뒤 적용을 승인했다.
아래는 **승인 후 코드에 적용된 대체표**다. 원본 마지막 페이지 구성은 미확보이며,
클라이언트/Vorbis는 변경하지 않았다. 서버 표시 목록과 실제 지급의 의미를
함께 검증해야 한다. 승인되지 않은 반복 지급은 추가하지 않았다.

모든 수량은 원본 복원이 아닌 승인된 운영 설정이며, 행마다 회차당 1회 지급한다.
기도 합계는 GP 800/1600, 조약돌 3/6, 혼옥 3/5이다.
요격 합계는 GP 800/1600, 수렵단 티켓 15/30이다.
0050 마이그레이션은 기도(type 1)/요격(type 6)의 회차·기준점별 보수 구간을
첫 수령 목록 요청 시 고정한다. HR2–4에서 발급된 단계는 HR5–7/GR 승급 후
추가 발급하지 않으며, 미수령 영수증은 유지한다. 아직 발급되지 않은 단계는
현재 랭크로 받을 수 있다. 기존 GR 기도 20000점 및 DB에 남아 있는 GR 요격
보수 ID에 대응하는 발급/수령 기록도 같은 그룹으로 보존한다.

기도는 원래의 GR/HR 상하한 필드로 두 HR 탭을 구분한다. 요격 목록에는
HR/GR 필드만 있으므로 HR 탭에 현재 캐릭터 구간의 5항목을 내려준다.
GR 캐릭터의 HR 탭 미리보기는 HR5–7 표를 쓰지만 HR 수령은 허용하지 않는다.
표시 목록을 다시 요청하면 현재 랭크를 DB에서 읽으며, 열려 있는 캐시 화면을
승급 순간에 강제로 새로고침하지는 않는다.

기도 표는 위 마지막 페이지 문제가 해결되기 전 표시까지 완성된 것으로
취급하지 않는다. 공지에서 단계별 1회 지급과 반복 안내 오류를 알린다.
GR의 품목·수량과 기존 수령 기록은 보존하며, 운영 DB 직접 변경/배포는 하지 않았다.

## 실행 중인 GR 화면 메모리 대조 (2026-09-22)

사용자가 GR1 탭을 열어 둔 `mhf.exe`에서 `ReadProcessMemory`만 사용했다.

  표시 인덱스는 `[10,11,12,13,14,15,-1,-1]`, 기준점 표시 플래그는
  `[1,0,0,0,0,0,0,0]`이다. 즉 첫 페이지가 곧 마지막 페이지다.

따라서 현재 화면의 **품목·수량은 정확하지만 반복 안내는 지급 정책과 다르다**.

현재 메모리는 우리 서버의 목록이며 원본 서비스의 마지막 페이지 근거는 아니다.

한국어 공지는 사용자의 수정 요청에 따라 '~입니다/~합니다/~없습니다'체로

## 서버 전용 해결 범위 재현 검증 (2026-09-22)

사용자가 **서버 수정만 허용**했으므로 Vorbis, 클라이언트 파일, 실행 중인
프로세스 메모리는 변경하지 않았다. 실제 x86 코드를 Unicorn 2.1.4의 격리된
메모리에서 실행해 목록 구성을 바꿔 보았다. Ghidra HTTP는 읽기 전용으로
사용했으며, 실험은 운영 DB나 게임 서버에 접속하지 않는다.

### 재현 방법과 결과

- 페이지 함수 `103b5570`, 보수 getter, HR 변환 함수와 상수표를 실행했다.
  `memset`은 동등한 메모리 초기화로 대체하고 보안 쿠키 검사만 생략했다.
  전체 화면을 그린 것은 아니며, 렌더러 `103b6509`의 실제 분기를 실행해
  반복 경로 `103b651d`/일반 경로 `103b657b` 중 어느 쪽인지 판별했다.
- 현재 18행을 입력했을 때 GR 결과가 실기와 일치했다: 총 1페이지,
  인덱스 `[10,11,12,13,14,15,-1,-1]`, 점수는 모두 20000, 반복 경로 선택.
- 행 수 1/2/6/8/9/16/24, 끝 플래그 0/1/2/255, 동일/상이한 기준점의

- 현재 GR6행의 플래그를 0/1로 바꾸는 64조합도 모두 같은 결과였다.
  끝 플래그는 페이지 구분에 영향을 줄 수 있으나 반복 표시를 끄지 않는다.
- 현재 HR2–4/HR5–7 목록도 각각 1페이지이며 반복 경로다. 첫 두 기준점이
  100/1000이므로 900 간격으로 잘못 표시할 수 있다. GR의 0 간격만을
  해결하려고 두 번째 기준점을 바꾸는 것은 HR과 지급 조건 문제를 해결하지 않는다.

실험의 페이지 코드 입력 범위는 `103b5570`부터 2560바이트이며 SHA-256은
`7fb9ecc88e6c6d7c66c46f83504b29d6c53df87cb99d67191e911798128bc7ee`이다.
렌더 분기 입력은 `103b6509`부터 32바이트이며 SHA-256은

이는 여러 대표 입력의 재현 검사이며 모든 비정상 패킷에 대한 전수 검사는 아니다.
정상 목록에 대한 결론은 반복 분기에 플래그 검사가 없다는 코드 분석과 함께 낸다.

### 서버 응답과 문구의 제어 범위

`11535320`은 `count:u16`과 19바이트 보수 행만 파싱한다. 반복 문구나
전체 페이지 수를 서버가 별도로 지정하는 필드는 없다. `103b5ec0`은
개인 달성 메뉴의 현재 페이지가 마지막이면 반복 문구를 선택하고, 첫 두
행의 기준점 차이를 반복 간격으로 넣는다. 이는 수령 가능 보수 응답과 별개다.

반복 문구는 `[[[DAT_1e77dccc + 0x110c] + 8] + 0x10]`에서 읽는다.
`DAT_1e77dccc`의 로더 `10afba10`은 `mhfpac` 파일을 읽고 검증·해제한
자원을 등록한다. 서버의 `GET_UD_INFO` 공지 문자열로 이 문구를 교체하는
경로는 해당 보수 응답 파서와 렌더러에 없다.

따라서 **현재 클라이언트에서 승인된 유한·단계별 1회 보수를 보존하면서,
정상적인 보수 목록 응답만으로 마지막 페이지 반복 안내를 없애는 수정은
불가능하다**. 보수를 추가하면 마지막 페이지가 뒤로 이동할 뿐이다.
서버가 실제 반복 구간을 제공하고 그에 맞는 수령 권리도 구현하는 것은
별도 방안이지만, 현재 정책을 바꾸며 원본 반복 조건도 아직 확보되지 않았다.
원본 자료를 더 확보하더라도 실제 지급 정책을 확인해야 하며, 자료 확보만으로
유한 표의 표시 문제가 해결된다고 약속하지 않는다.

이번 조사에서는 가짜 보수·도달 불가능한 기준점·패킷 범위 초과로 표시를
우회하지 않았다. 보수량, 지급 조건, 수령 기록은 그대로이며 표시 오류는
미해결이다. 기존 오류 안내 공지만 유지한다. 서버 검증 명령
`go test -race ./server/channelserver -run '^TestDiva' -count=1 -timeout=120s`는
통과했다. 이 테스트 통과는 게임 내 표시 문제가 해결되었다는 의미가 아니다.
