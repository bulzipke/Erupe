# 기도 개인 달성 로테이션: 서버 전용 구현 가능 범위

2026-09-22. Ghidra MCP HTTP(로컬 8089)의 읽기 전용 조회와 Unicorn 격리 실행으로
`mhfo-hd.dll.clean.mapped.bin`을 분석했다. 클라이언트 파일·실행 프로세스·운영 DB는
변경하지 않았다. 아래의 42,000/1,500은 **형식 실험 입력**이며 활성 보수 설정이 아니다.

후속: [HR 반복 보수 운영표와 표시 수정](diva-hr-prayer-rotation.md)을 구현했다.
HR 두 탭도 21,000점부터 실제 반복 지급을 하므로 아래 GR 구현 당시의
“HR 반복 안내 문제는 남음”이라는 상태는 후속 구현으로 해소했다.
원본 함수의 페이지 처리로 검증했으며 실제 게임 확인은 별도다. 기존 일회 표는 유지한다.

## 서버 구현 적용 (2026-09-22)

기존 GR 일회 보수 11행(최종 102,000점)은 그대로 보존하고, 이후 실제 반복
지급을 서버에 추가했다. 공유받은 24,000점 시작 표로 교체하지 않았다.
아래는 **원본 미확정 운영 대체안**이며 40회 원본 복원으로 분류하지 않는다.

| 달성 점수 | 추가 보수 |
| ---: | --- |
| 103,000 | 백은결정(0x2338) 5개 |
| 104,000 | 황금결정(0x2339) 5개 |
| 105,000 | 백은결정 5개 |
| 이후 매 1,000점 | 두 품목을 순서대로 반복 |

- GR1 이상, 해당 회차의 노래 구슬 원장 점수만 사용한다. 시작점은 포함한다.
  전체 누적 점수나 클라이언트가 보낸 수령 수량으로 자격을 계산하지 않는다.
- 과거 회차로 소급 지급하지 않는다. 현재 진행 중 회차에 이미 쌓은 점수가
  조건을 넘었으면 이번 업데이트 이후 조회할 때 그 회차의 반복 보수는 받을 수 있다.
- `0051_diva_prayer_rotation.sql`은 기존 표/수령 이력을 수정하지 않고 발급 순번
  테이블만 추가한다. 서버 시작 시 기존 자동 마이그레이션에 포함된다.
- 순번은 수령 완료가 아닌 **발급 완료 순번**이다. 영수증 삽입과 같은 트랜잭션에
  기록한다. 재조회·재접속·동시 요청 때 같은 점수의 보수를 새로 만들지 않는다.
- 일회 보수와 반복 보수를 합쳐 한 응답은 최대 32건이다. 미수령 자리를 채울
  만큼만 반복 영수증을 만들고, 수령 후 다음 조회에서 이어서 발급한다. 큰 점수를
  한 번에 펼쳐 메모리/DB에 수백만 행을 만들지 않는다.
- 기존 소재/GP 저장과 영수증 소비의 원자 처리에 연결한다. 저장 실패 시 수령
  권리는 남는다. 이 기능이 클라이언트 저장 전체를 서버 권위 인벤토리로 바꾸는
  것은 아니다. 기존 미수령 영수증의 수령 조건도 그대로 유지한다.
- `(캐릭터, 회차)`별 한 cursor에 스케줄 식별자와 수량/간격 fingerprint를 고정한다.
  회차 도중 정책을 바꾸면 조용히 재지급하지 않고 오류로 거절한다. 정책 변경은
  별도 마이그레이션 판단이나 다음 회차가 필요하다.
- uint32 점수 범위를 넘으면 상한을 적용한다. 반복 종료를 가리키는 원본 규칙은
  확인되지 않았으며 프로토콜 범위 안에서 조건을 달성한 만큼 계속 지급한다.

실제 직렬화한 25행을 원본 함수로 격리 실행한 결과, GR은 일반 8행/일반 3행/
반복 2행의 3페이지로 나뉜다. 마지막 페이지는 **103,000점 이후 1,000점마다**로
표시되어 서버 지급과 일치한다. 표시용 2행은 일회 지급 계산에서 제외한다.
이것은 페이지 계산/렌더 분기 검증이며 실제 게임 접속 후 수령 확인은 별도이다.

HR2–4/HR5–7은 기존 운영표와 지급 정책을 유지한다. 두 HR 탭의 기존 마지막
페이지 반복 문구 문제는 이번 GR 구현으로 해결되지 않는다. HR 반복 표와
경계 배열을 별도로 검증하지 않고 임의의 보수를 추가하지 않았다.

검증 기록:

- `go build ./...` 통과.
- 격리 PostgreSQL에서 `go test -race ./server/channelserver -run '^Test(Diva|RepoDiva)'`
  통과(68.154초). 신규 9개 DB 테스트 그룹은 건너뛰지 않고 실행했다.
- 8개 동시 조회, 부분/전체 배치 수령, 재접속, 발급/저장 실패, 회차/캐릭터
  분리, 랭크 변경, 정책 불일치와 `MaxInt64` 점수에서의 32건 상한을 검사했다.
- 신규 0051 마이그레이션의 기존 영수증 보존/재실행/제약 검사 통과.
  전체 마이그레이션 검사는 기존 `TestMigrateExistingDBWithoutSchemaVersion`만
  실패했다. 버전 표를 지운 뒤 기존 0034를 다시 실행하면 `raviente_runs`

  해당 기존 검사를 제외한 마이그레이션 검사는 모두 `-race` 통과했다.
- 운영 DB·클라이언트·배포 파일은 변경하지 않았다. 인게임 최종 수령 확인은 남아 있다.

## 결론

서버에서 **실제 반복 보수를 계산하고**, 클라이언트의 반복 목록 형식에 맞게
안내하는 것은 가능하다. 앞서 불가능하다고 한 범위는 **일회 지급을 보존하면서
마지막 페이지의 반복 문구만 없애기**였다. 두 결론은 구분해야 한다.

클라이언트는 보수 목록을 서버에서 받아 표시한다. DLL에서 40회의 시작점·간격·
품목·수량·끝점을 복원하는 것은 이번 함수 분석으로 가능해지지 않는다. 표시를
복원할 수 있다는 것과 원본 지급 정책을 알아냈다는 것은 다르다.

## 원본 함수 격리 실행 결과

기존 실기와 일치했던 18행 재현을 대조군으로 유지하고, 일반 행 수 0/1/2/6/8/9와
반복 행 수 1/2/3/6/8의 30조합 및 혼합 사례를 검사했다. 전체 화면을 렌더링한
검사가 아니라 **페이지 인덱스·기준점·실제 렌더 분기**를 실행한 검사다.
추가 혼합·HR 경계·보완 카탈로그·8행 초과 사례까지 45개 입력을 실행했고,
보완 목록의 페이지 배치와 HR 경계 보정 사례의 단언 검사도 통과했다.

대표 사례: 일반 GR 20,000점 6행 뒤에, 점수 42,000/43,500인 두 행을 각각
마지막 플래그 1로 넣는다.

| 페이지 | 선택된 행 | 표시 경로 |
| --- | --- | --- |
| 1/2 | 기존 20,000점 6행 | 일반 단계 표시 |
| 2/2 | 42,000, 43,500점 2행 | 시작점 42,000 / 간격 1,500의 반복 표시 |

일반 행이 있고 반복 꼬리가 2~8행인 실험에서는 꼬리가 별도 마지막 페이지로
분리됐다. 임계점은 균등해야 하지만 **클라이언트가 균등 여부를 검증하지는 않는다**.
42,000/43,500/60,000을 넣어도 문구 간격은 첫 두 행 차이인 1,500이다.
같은 점수 두 행이면 다시 간격 0이 된다.

주의점:

- 반복이 한 행뿐이면 두 번째 기준점이 없어 정상적인 간격을 표현하지 못한다.
  일반 페이지와의 분리도 보장되지 않는다.
- 반복 9/10/16행 실험에서는 여러 페이지로 갈리고 마지막 페이지의 첫 두 행을
  다시 기준으로 삼는다. 한 순환 전체를 보여주는 형식으로는 2~8행을 검증해야 한다.
- 일반 행 없이 index 0부터 반복 3행 이상을 넣으면 첫 행이 일반 페이지로
  떨어지는 예외가 있다. `103b57e0..5805`의 이전 인덱스 탐색은 index 0을 제외한다.
- 서버가 점수순으로 미리 정렬하지 않으면 클라이언트 행 교환에서 플래그와
  보수의 대응이 깨질 수 있다. 현재 서버의 점수 오름차순 정렬은 유지해야 한다.
- 표시용 꼬리는 일반 단계들 **뒤**에 와야 한다. 102,000점 일반 보수가 있는
  현재 표에 실험용 42,000점 꼬리를 그대로 붙이는 것은 올바른 운영안이 아니다.

### HR 두 구간이 섞이는 경우

반복 경계의 이전 행 탐색은 HR/GR 바이트만 비교하고 HR 상하한을 비교하지
않는다. 두 HR 탭의 행을 점수순으로 섞고 반복 플래그를 모두 1로 주면,
HR5~7의 마지막 일반 20,000점 보수가 반복 페이지에 끼어들었다.

동일 실험 입력에서 첫 HR2~4 꼬리 행만 플래그 0, 나머지는 1로 주자 세 탭
모두 일반/반복 페이지가 의도대로 분리됐다. 이는 **해당 입력의 재현 결과**이지
모든 배열에 쓸 수 있는 일반 규칙으로 확정한 것은 아니다. 향후 구현에서는
세 탭의 최종 직렬화 결과를 함께 검증해야 한다. GR만 검사해서 완료로 보지 않는다.

## 현재 보수 보완과의 관계

[블로그 단일 임계점 5행](diva-blog-reward-audit.md)을 더하면 GR은 총 11행이 된다.
격리 실행에서는 1/2페이지에 20,000점 6행과 24,500/29,500점,
2/2페이지에 99,000/100,500/102,000점이 들어갔다.

**마지막 화면은 99,000 이후 1,500마다라는 반복 문구를 여전히 표시한다.**
이번 추가는 과거 보수의 내용 보완이지 반복 표시 오류 해결이 아니다. 실제
서버 지급은 새 항목도 회차당 한 번뿐이며, 103,500점 이상이라고 이를 반복 지급하지 않는다.
기존 20,000점 영수증·품목·수량과 HR 승인 대체표는 보존한다.

## 실제 반복 구현에 남은 결정

서버가 달성 점수에서 지급 순번을 계산하고 `순번 % 품목수`로 순환시키는 것은
구현 가능한 모델이다. 다만 **이 계산식 자체를 40회 원본으로 확인한 것은 아니다**.
다음 값은 별도 자료 또는 운영 정책으로 정해야 한다.

1. 반복 시작 점수와 첫 지급 시점(시작점 포함 여부).
2. 양수 간격, 품목 순서와 수량, 끝점/최대 반복 수 또는 실제 무제한 여부.
3. HR2~4/HR5~7/GR별 구성과 승급 시 동일 순번 중복 수령 방지.
4. 기존 일회 지급과 반복 경계에서의 중복 여부.

실제 반복을 추가한다면 회차·캐릭터·스케줄 버전·순번으로 영구 키를 만들고,
32건씩 나누어 발급해야 한다. 기존 소재/GP 저장 트랜잭션에 수령 확정을 연결하고,
재접속·재조회·표 변경으로 이미 받은 순번이 재발급되지 않게 해야 한다.
이 결정 없이 표시만 맞추는 가짜 보수나 무한 GP 지급은 활성화하지 않았다.
